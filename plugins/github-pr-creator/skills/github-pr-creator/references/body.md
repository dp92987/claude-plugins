# Тело PR без шаблона

Тело состоит из пяти частей в этом порядке, других нет. Заголовки секций есть
только у «Деплоя» и «Отката»: их ищут глазами в момент выкатки и в момент
инцидента, описание читается сверху вниз.

```markdown
<ссылка на тикет>

<описание — текст для человека: что меняет этот PR>

## Деплой

**До деплоя**
1. …

**Деплой**
1. `<сервис>` → `<кластер>`, `<кластер>`. <почему на этом месте>

**После деплоя**
1. …

## Откат

1. …

---

🤖 Generated with <инструмент> (<модель>)
```

## Ссылка на тикет

Первая строка тела — полный URL: `<сайт Jira>/browse/<KEY-123>`. Без
заголовка и без текста вокруг: GitHub делает URL кликабельным сам, а
голый ключ — нет. Ключ берётся из имени ветки, сайт — из `config.md`.

## Описание

Текст для коллеги из команды. Предметную область и систему он знает, сессию —
нет. Прочитав описание, он понимает, что меняет PR, и дальше сам смотрит в
коде, как именно. Описание излагает суть изменения понятным языком:

- **что меняется в поведении системы** — было так, стало так. Словами
  предметной области, а не путями к полям;
- **как это устроено в общих чертах** — на чём держится решение, если без
  этого изменение непонятно: например, переходный период для старых данных или
  выключатель в конфиге. Без подробностей, которые и так видны в коде.

Описание рассказывает, а не направляет. В нём нет указаний, что тут главное и
на что смотреть: «главное место для ревью», «стоит проверить», «обратите
внимание». Что важно, читатель решит сам, а подсказка сужает его взгляд до
того, что автор и так считал верным. Командный контекст не объясняется заново:
сервисы, сущности и термины, которые коллеги знают, называются, а не
расшифровываются.

Пишется связным текстом, абзацами; список — только когда пунктов правда
несколько и они равноправны. Обычно хватает одного-трёх абзацев.

Идентификаторы в бэктиках — только там, где они помогают найти место в диффе
или назвать то, что нужно знать при деплое: сервис, ключ конфига, топик,
таблица. Абзац, в котором бэктиков больше, чем слов, — признак пересказа кода:
перескажи смысл.

Чего в описании нет:

- пересказа диффа по файлам — ревьюер видит вкладку Files;
- пересказа тикета — «зачем» живёт по ссылке строкой выше;
- истории работы: прогонов тестов и линтера, кругов ревью, отброшенных
  вариантов, «исправлено после замечания». Это процесс, а не изменение;
- отдельных секций «Проверено», «Решения», «Замечания», «Тесты», «Риски»:
  решение, без которого изменение непонятно, — фраза в описании, а не секция;
- указаний ревьюеру, что важно и куда смотреть;
- причин, которые уже записаны в комментариях к коду.

Описание читается без кода под рукой: если фразу нельзя понять, не открыв
файл, её нужно переписать.

## Деплой

Три блока во временном порядке. У каждого одна форма: подпись жирным, под ней
нумерованный список. Порядок пунктов внутри блока — порядок действий. Пустой
блок — слово «Нет.» на месте списка; сам блок не пропадает. Ревьюер находит
каждый блок на одном и том же месте в каждом PR, а «Нет.» говорит, что автор
проверил и ничего не нашёл. Пропущенный блок этого не говорит.

### До деплоя

Что должно существовать раньше, чем код окажется на проде. Каждый пункт —
действие с точным именем сущности:

- секрет: имя, путь в хранилище, для какого сервиса; значение — никогда;
- ключ конфига: сервис, имя ключа, откуда взять значение («как у `X` в том же
  файле») — само значение только если оно не секрет и пользователь его назвал;
- внешняя сущность: топик, очередь, бакет, DNS-запись — где заводится; если
  отдельным PR в другом репозитории — ссылка на тот PR;
- миграция, которую накатывают руками до кода.

### Деплой

Один пункт на сервис, в порядке деплоя. Форма пункта: имя сервиса в бэктиках,
стрелка `→`, прод-кластеры через запятую в бэктиках, точка, пояснение. Пояснение
говорит, почему сервис стоит на этом месте: «консьюмер должен подняться раньше
продюсера», «миграция накатывается при старте». Порядок не важен — пояснения
нет.

В списке — только сервисы, которые нужно выкатить, чтобы изменение заработало.
Сервис, который пересобирается из-за правки общего пакета, но ведёт себя
по-прежнему, в список не входит: пункт в этом блоке читается как «катить».
Когда катить нечего, вместо списка — «Не требуется:» и причина одним
предложением («поведение сервисов не меняется, данные читать некому до
ABC-124»); сервисы, которые подхватят изменение при очередной выкатке, при
желании перечисляются в том же предложении как факт.

Кластеры — только прод, из манифеста деплоя сервиса. Dev-контур не пишется:
он есть почти у всех. Отклонения пишутся в конце пункта: «без dev», когда
dev-контура у сервиса нет; «не деплоится», когда сервис не идёт ни в один
кластер.
Кластеры с другим назначением (крон, мультипёрпос) — тоже прод, без пометок.

Список кластеров у каждого сервиса свой и стоит в его пункте. Общего списка на
всю секцию нет: он либо врёт, что каждый сервис деплоится везде, либо не несёт
информации.

### После деплоя

Что делается, когда код уже на месте: включить флаг, задеплоить консьюмер,
удалить старый ключ, посмотреть метрику через сутки. Поэтапное включение по
контурам пишется здесь, и здесь dev упоминать можно: это этап, выбранный
автором, а не список кластеров.

## Откат

Как вернуть систему в состояние до PR, если после выкатки что-то пошло не так.
Секция обязательна, как и «Деплой»: её читает дежурный посреди инцидента, когда
разбираться в диффе некогда, а автор PR может быть недоступен. Форма —
нумерованный список действий в порядке выполнения.

- **Выключатель первым.** Если изменение закрыто флагом или ключом конфига,
  первый шаг — выключить его: это быстрее выкатки и не трогает остальное. Имя
  флага и где он живёт.
- **Предыдущая версия сервисов** — по пунктам «Деплоя». Порядок отката
  пишется, только когда он важен, с причиной: «сначала вернуть продюсер, иначе
  старый консьюмер получит события нового формата».
- **Что выкаткой не откатывается** — называется явно, каждое с тем, что с ним
  делать:
  - миграция: есть ли down-миграция и накатывается ли она сама; нет —
    «необратимо» и совместима ли новая схема со старым кодом;
  - данные, которые новый код уже записал, и события, ушедшие в топик: прочтёт
    ли их старая версия;
  - ключи конфига и секреты, удалённые «После деплоя»: их нужно вернуть до
    выкатки старой версии.
- **Сущности из «До деплоя»** — топики, секреты, новые ключи — при откате
  обычно остаются: старый код их не читает. Это пишется одной строкой, чтобы
  дежурный не удалял их в спешке.

Каждое утверждение о совместимости проверено по коду: down-файл миграции
существует, старая версия читает поле как необязательное, консьюмер
пропускает незнакомый тип события. Не проверено — это вопрос на шаге 7, а не
строка «должно работать» в теле: на ней дежурный примет решение откатываться.

Откат без побочных эффектов — один пункт и одна строка факта: «Выкатить
предыдущую версию `schedule`. Миграций, флагов и данных в новом формате нет.»
Вторая фраза — не формальность: она говорит, что автор проверил и ничего не
нашёл.

Когда «Деплой» — «Не требуется», откат тоже не выкатка: «Не требуется:» и
что делать при ошибке — обычно revert PR, который уедет с очередной выкаткой
тех же сервисов.

## Пример 1: два сервиса, секрет, миграция, внешняя зависимость

```markdown
https://example.atlassian.net/browse/ABC-5312

Сейчас карточка заказа узнаёт о новом статусе рейса, только когда сама
перечитывает подписку, — до получаса задержки. После этого PR `schedule`
сообщает об изменении статуса сразу: пишет событие в новый топик
`schedule-exports`, а `orders` читает его и обновляет карточку.

Если Kafka недоступна, продюсер делает три попытки с бэкоффом, а потом кладёт
событие в таблицу-outbox, откуда его дошлёт фоновый воркер. Изменение статуса
при сбое брокера не теряется и не блокирует обработку подписки.

Экспорт выключен флагом: сначала выкатываются оба сервиса, потом флаг
включается — по контурам, см. «Деплой».

## Деплой

**До деплоя**
1. Создать топик `schedule-exports` в Kafka каждого контура — PR в
   `infra-repo`: https://github.com/org/infra-repo/pull/482.
2. Завести секрет `KAFKA_EXPORT_SASL_PASSWORD` для `schedule` в Vault по
   пути `secrets/schedule/kafka` — в prod пока нет.
3. Добавить в конфиг `orders` ключ `schedule_exports.consumer_group`,
   значение — как у `live_activity.consumer_group` в том же файле.

**Деплой**
1. `schedule` → `us-east-1`, `eu-central-1`, `ru-central-1`. Миграция
   `20260902_export_outbox.up.sql` накатывается при старте и создаёт таблицу
   outbox; продюсер пока выключен флагом.
2. `orders` → `us-east-1`. Консьюмер должен подняться раньше, чем продюсер
   начнёт писать, иначе первые события потеряются.

**После деплоя**
1. Включить флаг `schedule_exports_enabled` в `schedule` на dev.
2. Через сутки без роста `schedule_export_failed_total` включить флаг в
   остальных кластерах `schedule`.

## Откат

1. Выключить флаг `schedule_exports_enabled` в `schedule` во всех кластерах:
   продюсер перестаёт писать в `schedule-exports`, этого обычно достаточно.
2. Если нужно убрать код — выкатить предыдущие версии `schedule` и `orders`.
   Порядок не важен: продюсер уже выключен флагом.
3. Таблица `schedule_export_outbox` остаётся: down-миграции нет, старая
   версия `schedule` таблицу не читает. Топик и секрет тоже остаются.

---

🤖 Generated with Claude Code (Fable 5.1)
```

Что здесь важно:

- описание начинается с того, что меняется, а не со списка файлов; путь к
  схеме события и имя таблицы читатель найдёт в диффе;
- устройство пересказано в общих чертах — топик, поведение при сбое, флаг, —
  без указаний, какое место тут главное;
- секрет назван по имени и пути, без значения; «в prod пока нет» — факт из
  сессии, подтверждённый пользователем до создания;
- ссылка на PR в другом репозитории стоит целиком: её спросили до создания, а
  не оставили плейсхолдер;
- пояснение у каждого пункта «Деплоя» объясняет позицию, а не пересказывает
  дифф;
- «После деплоя» упоминает dev как этап включения флага — это действие
  автора;
- «Откат» начинается с флага, а не с выкатки, и прямо называет то, что
  выкаткой не уберётся: таблицу без down-миграции.

## Пример 2: катить нечего

```markdown
https://example.atlassian.net/browse/ABC-5318

Карточка рейса теперь помнит, почему показала тот или иной статус и откуда
взяла каждое время: из расписания, от авиакомпании или из нашей корректировки.
Это заготовка для аналитики: сейчас эти данные никуда не уходят, клиенты
получают карточку в прежнем виде, а читать их начнёт воркер из ABC-5320.
Параметры заполняются там же, где выбирается показ, поэтому совпадают с тем,
что увидел пользователь.

## Деплой

**До деплоя**
Нет.

**Деплой**
Не требуется: поведение сервисов не меняется, новые данные читать некому до
ABC-5320. Изменение уедет с очередной выкаткой `trips`, `orders` и
`live-activity-worker` (`ru-central-1`).

**После деплоя**
Нет.

## Откат

Не требуется: выкатывать нечего. Ошибка найдётся — revert PR, он уедет с
очередной выкаткой тех же сервисов.

---

🤖 Generated with Claude Code (Fable 5.1)
```

Три сервиса пересобираются из общего пакета, но пунктами «Деплоя» не стали:
ни один из них не нужно выкатывать, чтобы изменение заработало. Они названы
одной строкой как факт — чтобы деплоящий не искал, куда изменение уедет.

## Пример 3: один сервис, ничего вокруг

```markdown
https://example.atlassian.net/browse/ABC-5320

Подписки, созданные уже после вылета рейса, не помечались прошедшими: признак
«вылет прошёл» сравнивал текущее время со временем создания подписки, а не со
временем вылета. Теперь сравнение идёт с вычисленным временем вылета, и такие
подписки помечаются прошедшими сразу.

## Деплой

**До деплоя**
Нет.

**Деплой**
1. `schedule` → `us-east-1`, `eu-central-1`, `ru-central-1`.

**После деплоя**
Нет.

## Откат

1. Выкатить предыдущую версию `schedule`. Миграций, флагов и данных в новом
   формате нет.

---

🤖 Generated with Claude Code (Fable 5.1)
```

Описание — один абзац: маленький фикс не раздувается до трёх. Все три блока
«Деплоя» на месте, «Откат» — один пункт с проверенным фактом. Пункт «Деплоя»
без пояснения: сервис один, порядок не важен. Тело на четыре строки длиннее,
чем один абзац «деплоить как обычно», но глаз ревьюера находит блоки там же,
где в любом другом PR.
