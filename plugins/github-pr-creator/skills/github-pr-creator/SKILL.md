# Pull request в GitHub

Скилл создаёт PR из текущей ветки: заголовок, тело, базовая ветка. Больше
ничего: лейблы, ревьюеры, draft, assignee и milestone — решения автора о
процессе команды, и он ставит их руками. Неверно запрошенный ревьюер — шум для
живого человека, а неверный лейбл ломает чужие фильтры; ни то, ни другое не
стоит экономии одного клика.

Тело PR — главное. Ревьюер приходит в PR с двумя вопросами: «что тут сделано» и
«как это катить». На «зачем» отвечает тикет Jira, поэтому тело его не
пересказывает, а даёт ссылку. Всё остальное в теле — три вещи: короткое «что
сделано», строка «Проверено» и секция «Выкатка». Формат и примеры — в
`references/body.md`, прочитай его перед тем, как писать тело.

## Правило первое: сначала факты, потом текст

Каждый факт в теле проверен в первоисточнике до того, как попал в текст:

- список сервисов — назван в сессии и сверен с диффом;
- прод-кластеры сервиса — прочитаны из его манифеста деплоя в репозитории, а не
  из памяти и не из сессии: тот, кто писал код, в манифесты не заглядывал;
- новые ключи конфига и секреты — найдены в диффе, каждый проверен grep по коду;
- строка «Проверено» — то, что реально запускалось в сессии, с результатом;
- ключ тикета — из имени ветки, а не по памяти.

Непроверенный факт в тело не пишется. Вместо него — вопрос пользователю до
создания PR (шаг 7). Плейсхолдер «уточнить», «TODO» или пустая строка в теле не
допускаются: «Выкатка» с пропуском читается как «выкатывать нечего», и первым
это узнает тот, кто катит.

Значение секрета не попадает в тело никогда — ни из диффа, ни из сессии, ни из
манифеста. В теле стоят имя секрета и путь в хранилище. PR читают все, у кого
есть доступ к репозиторию, и история PR не чистится.

## Шаги

### 0. Найти сайт Jira

Каталог данных плагина — `${CLAUDE_PLUGIN_DATA}`. Если переменная не
подставлена, каталог ищется как
`~/.claude/plugins/data/github-pr-creator-<marketplace>/`.

1. Прочитай `config.md` в каталоге данных: таблица «репозиторий → URL сайта
   Jira».
2. Определи репозиторий: `git remote get-url origin`, нормализованный до вида
   `github.com/org/repo` (без схемы, `git@`, двоеточий и `.git`).
3. Возьми URL по точному совпадению строки.

Строки нет — спроси URL сайта (`https://<site>.atlassian.net`) один раз и
допиши строку в таблицу сам. Файла нет — создай его с заголовком таблицы. Это
единственная настройка скилла: всё остальное он читает из репозитория и из
сессии.

### 1. Ветка, тикет, база

- Текущая ветка: `git branch --show-current`. Если это ветка по умолчанию
  репозитория — остановись и скажи: PR из мастера в мастер не бывает.
- Ключ тикета: первое совпадение `[A-Z][A-Z0-9]+-[0-9]+` в имени ветки. Ключа нет
  — спроси его на шаге 7. Ссылка на тикет в PR обязательна: без неё ревьюер не
  найдёт «зачем», а тело «зачем» не содержит.
- Базовая ветка: ветка по умолчанию —
  `git symbolic-ref --short refs/remotes/origin/HEAD`, при ошибке
  `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`. Другая база
  только если пользователь её назвал: PR в стеке — его решение, не твоё.
- `git fetch origin <база>`, затем `git log --oneline origin/<база>..HEAD` и
  `git diff origin/<база>...HEAD --stat`. Это и есть содержимое PR. Пустой лог —
  остановись: коммитов для PR нет.

Незакоммиченные изменения в PR не попадут. Если в рабочем дереве есть правки
файлов, которых касалась сессия, назови их на шаге 7: пользователь решает,
коммитить их или нет. Коммиты сам не делай.

### 2. Что сделано

Источник — сессия и дифф. Сессия говорит, что и зачем менялось; дифф — что
реально вошло. Прочитай дифф целиком, если он меньше нескольких сотен строк,
иначе по файлам, которые сессия называла. Абзац «что сделано» пишется по диффу,
а не по памяти о том, что собирались сделать: план и результат расходятся чаще,
чем кажется.

Строка «Проверено» — только то, что запускалось: команда теста, ручной прогон с
результатом. Ничего не запускалось — так и пиши: «Проверено: не проверялось».
Это честнее пропуска: пропуск читается как «проверено, но не написал».

### 3. Сервисы и кластеры

Список сервисов бери из сессии: агент, который писал код, знает, что он менял и
что от этого нужно катить. Сверь список с диффом: сервис назван, а в его дереве
и в общих пакетах изменений нет — спроси; дифф трогает сервис, которого в списке
нет — спроси. Сессия сервисов не называет — выведи их из путей диффа и подтверди
на шаге 7.

Для каждого сервиса найди его манифест деплоя в репозитории и прочитай список
целевых кластеров. Как манифест называется и где лежит — зависит от репозитория;
ищи рядом с точкой входа сервиса и в каталогах деплоя. Если список кластеров
записан через переменные пайплайна, найди в репозитории место, где они
определены, и раскрой. Не встраивай в свой ответ имена файлов и аннотаций из
одного репозитория: в другом они другие.

В тело идут только прод-кластеры. Dev-контур есть почти у каждого сервиса, и
строка, которая есть везде, ничего не различает. Упоминается только отклонение
от нормы: у сервиса нет dev-контура — пометка «без dev»; сервис не деплоится
никуда — «не деплоится».

Манифеста нет или список кластеров из него не читается — спроси на шаге 7.

### 4. Конфиги и секреты

Найди в диффе:

- новые ключи конфига: новые поля в структурах конфигурации, новые чтения
  переменных окружения, новые записи в файлах конфигов;
- новые секреты: новые ссылки на хранилище секретов, новые `secretKeyRef` и
  подобное в манифестах;
- миграции схемы данных;
- новые внешние сущности, которые должны существовать до выката: топики, очереди,
  бакеты, DNS-записи.

Для каждой находки реши, куда она идёт: «До выката» — то, что должно быть
готово раньше кода; «После выката» — то, что делается, когда код уже на месте
(включить флаг, докатить консьюмер, удалить старый ключ). Если сущность
заводится PR в другом репозитории — назови репозиторий и попроси ссылку на тот
PR на шаге 7.

WARNING: значение секрета — из диффа, из сессии, из тестового конфига — в тело
не копируется. Только имя и путь.

### 5. Заголовок

Формат — `<type>(<scope>): <KEY-123> <summary>`. Типы — из гайда Angular,
список в `references/commit-types.md`. `scope` — сервис или домен, которого
касается PR; два сервиса одного домена — домен. `summary` — в императиве, с
маленькой буквы, без точки в конце, на английском.

Если `README.md` или `CONTRIBUTING.md` репозитория задаёт свой формат заголовка
PR, он выигрывает: заголовок PR становится заголовком squash-коммита, и по нему
работает автоматика репозитория. Проверь эти файлы до того, как писать
заголовок.

### 6. Тело

Есть ли в репозитории шаблон PR: `.github/PULL_REQUEST_TEMPLATE.md`,
`.github/pull_request_template.md`, каталог `.github/PULL_REQUEST_TEMPLATE/`,
`docs/pull_request_template.md`, `PULL_REQUEST_TEMPLATE.md` в корне.

**Шаблона нет** — тело по `references/body.md`: ссылка на тикет, абзац «что
сделано», строка «Проверено», секция «Выкатка» из трёх блоков, футер.

**Шаблон есть** — строго по нему. Секции шаблона заполняются его порядком и его
заголовками, своих секций не добавляется, «Выкатки» тоже: шаблон — решение
команды о том, что она хочет видеть в PR. HTML-комментарии с подсказками автору
вырезаются: это инструкция, а не текст. Ссылка на тикет ставится в секцию про
контекст или тикет; нет такой — рядом с описанием изменений. Футер атрибуции —
последней строкой в любом случае.

Язык тела — русский. Шаблон на английском — тело на английском: смешение
языков в одном документе хуже любого из двух.

### 7. Выяснить всё открытое

Собери всё, что осталось неизвестным по шагам 1–4, в один список и задай
пользователю за один раз: ключ тикета, незакоммиченные файлы, расхождение
сервисов с диффом, кластеры без манифеста, ссылки на PR в других репозиториях,
порядок выката, если он не очевиден из зависимостей.

Круг один. Ответы ложатся в тело. Открытых вопросов в созданном PR не бывает:
PR — это заявка «готово к ревью», и вопрос в нём означает, что не готово. Если
пользователь отвечает «не знаю, создавай» — пиши в теле ровно это словами
(«порядок выката не определён, спросить у автора»), а не плейсхолдер.

Список пуст — сразу к созданию.

### 8. Запушить и создать

1. Проверь, что ветка запушена и не отстаёт: `git rev-parse @{u}` должен
   существовать и совпадать с `HEAD`. Иначе `git push -u origin <ветка>`.
   Пуш — часть просьбы «создай PR», отдельного разрешения не требует; PR без
   запушенной ветки не существует.
2. Запиши тело в файл в каталоге scratchpad: тело многострочное, с бэктиками и
   кавычками, через `--body` оно ломается в shell.
3. `gh pr create --title "<заголовок>" --body-file <файл> --base <база>`.

Подтверждения перед созданием не жди: просьба «создай PR» — это и есть
разрешение, а всё спорное выяснено на шаге 7. PR обратим: тело правится через
`gh pr edit`, ненужный PR закрывается одной кнопкой.

### 9. Отчитаться

Одна строка — ссылка на PR. Тело в чате не повторяй: пользователь откроет PR и
увидит его там, где увидят ревьюеры.

## Правка существующего PR

По просьбе «перепиши описание PR», «обнови тело» — и только по просьбе.
Порядок: `gh pr view --json title,body,baseRefName` → собери новую версию
целиком по шагам 2–7 → покажи её в чате → дождись «да» →
`gh pr edit --body-file <файл>` и при необходимости `--title`.

Чтение обязательно: `gh pr edit --body` перезаписывает тело целиком, и без
чтения ты не дописываешь, а стираешь. Показ перед записью нужен, потому что
существующий PR уже могли прочитать ревьюеры: замена текста под ними — не
то же самое, что первая публикация.

Чужие PR по своей инициативе не трогай.

## Футер атрибуции

Тело заканчивается горизонтальной чертой и строкой атрибуции:

```markdown
---

🤖 Generated with <инструмент> (<модель>)
```

Инструмент — тот, в котором ты работаешь (`Claude Code`). Модель — имя модели
из твоего собственного контекста, без суффикса про размер окна: `Opus 5`,
`Fable 5.1`, `Sonnet 5`. Читатель должен видеть, чем написан текст: у моделей
разное качество описаний, и это влияет на то, насколько телу верят.

## Границы

- Один вызов — один PR из текущей ветки. Несколько PR — несколько вызовов, по
  одному на ветку.
- Скилл не коммитит, не мержит, не ребейзит, не переключает ветки. Ветку он
  только пушит.
- Скилл не ставит лейблы, ревьюеров, draft, assignee, milestone, project — даже
  по просьбе он говорит, что это делается руками, и называет флаг `gh`, которым
  это делается.
- Скилл не создаёт и не правит тикеты Jira. Ссылка на тикет — единственное, что
  связывает PR с Jira; сама связь на стороне Jira появляется по ключу в
  заголовке, если у команды настроена интеграция.

## Файлы скилла и данные

Настройка — вне плагина, в `${CLAUDE_PLUGIN_DATA}/config.md`: таблица
«репозиторий → URL сайта Jira», которую скилл ведёт сам.

- `references/body.md` — формат тела без шаблона: абзац «что сделано», строка
  «Проверено», три блока «Выкатки» с правилами для каждого, два разобранных
  примера. Читать перед тем, как писать тело.
- `references/commit-types.md` — типы заголовка из гайда Angular, правила
  `scope` и `summary`, примеры заголовков. Читать на шаге 5.
