# Тикет в Jira

Скилл создаёт тикет: поля по командным умолчаниям плюс описание, по которому
исполнитель начинает работу, не имея доступа к этому чату.

Скилл не привязан к конкретной Jira. Всё проектное — сайт, `cloudId`, ключ
проекта, id типов, полей и связей, компоненты, словарь лейблов, правила
заголовка, шкала оценки, доска спринтов, язык текста — живёт в **профиле**:
markdown-файле в каталоге данных плагина. Здесь описан только порядок работы, и
каждый шаг берёт значения из разделов профиля по их именам.

Главная ценность здесь — описание, а не поля. Тикет живёт дольше сессии: его
читают через месяц, по нему работает другой человек или агент в чистом контексте.
Поэтому описание не пересказывает разговор, а заменяет его.

## Правило первое: сначала факты, потом текст

Каждый факт в описании проверен в первоисточнике до того, как попал в текст:

- путь к файлу, имя метода, текущий код — открыты в репозитории;
- число («7 срабатываний в сутки», «14 из 191 счёта за 30 дней») — снято
  измерением, и в тексте стоит рядом с датой измерения;
- ключ Jira в ссылках — назван пользователем или найден в коде и коммитах, а не
  собран по памяти; выдумывать ключи нельзя, но и проверять их запросом не нужно:
  неверный ключ отклонит сам вызов создания связи;
- ссылка на тред или заказ — дана пользователем или найдена, не собрана из
  догадки.

Непроверенный факт не пишется вообще. Вместо него — либо явная строка «нужно
проверить: …», либо вопрос пользователю. Ошибочный путь к файлу в тикете дороже
отсутствующего: он уводит исполнителя в неверное место с полной уверенностью.

Правило касается фактов, которые ты утверждаешь, и только их. Ненайденное решение
— не пробел: задача говорит, что нужно сделать, а как — решает исполнитель (см.
шаг 4). Не путай «не проверил» с «не моё решение».

Когда пользователь просит тикет «по тому, что мы только что обсуждали», источник
фактов — эта сессия, но пути, имена и числа всё равно перечитываются в коде и в
данных. В сессии они могли измениться или быть названы приблизительно.

## Шаги

### 0. Найти профиль

Каталог данных плагина — `${CLAUDE_PLUGIN_DATA}`. Если переменная не
подставлена, каталог ищется как
`~/.claude/plugins/data/jira-ticket-creator-<marketplace>/`.

1. Прочитай `config.md` в каталоге данных: там маппинг «репозиторий → профиль».
2. Определи репозиторий: `git remote get-url origin`, нормализованный до вида
   `github.com/org/repo` (без схемы, `git@`, двоеточий и `.git`).
3. Выбери профиль по точному совпадению remote. Wildcard-строк и профиля по
   умолчанию нет намеренно: молча выбранный чужой профиль уводит тикет не в ту
   Jira.
4. Прочитай `profiles/<имя>.md` целиком. Дальше шаги ссылаются на его разделы:
   «Сайт», «Jira-проект», «Язык», «Типы задач», «Кастомные поля», «Компоненты»,
   «Лейблы», «Заголовок», «Оценка», «Спринты», «Связи».

Раздела нет в профиле — скилл этим полем не управляет: поле не заполняется, и в
отчёте это названо прямо. Значение из другого профиля или из памяти не
подставляется.

**Профиль не нашёлся** (нет config.md или в нём нет строки для этого remote):
тикет не создавай. Скажи, что репозиторий не привязан к профилю, и предложи
`/jira-ticket-creator:setup` — команда создаёт профиль и строку маппинга.
Только если пользователь явно просит разовый тикет без настройки: спроси сайт
(или `cloudId`) и ключ проекта, создай минимальный тикет — проект, тип,
заголовок, описание — и перечисли, какие поля не проставил.

**Другой Jira-проект того же сайта** (пользователь назвал другой ключ): из
профиля верны сайт и, как правило, типы задач и типы связей. Компоненты, лейблы,
доска и спринты — свои. Создай минимальный тикет и скажи, что не проставил. Не
переноси на чужой проект профиль команды: молча проставленный чужой компонент
хуже непроставленного.

**Другой сайт Jira**: `cloudId` из профиля не годится. Спроси его — не
подставляй знакомый, иначе тикет уедет не в ту Jira, и заметить это будет нечем.

Правила письма — форма описания по типу, футер, «сначала факты» — действуют
всегда: они не часть профиля. Язык текста задаёт раздел «Язык» профиля; без
профиля пиши на языке пользователя.

### 1. Собрать факты

Определи по запросу пользователя: тип работы, затронутый репозиторий и файлы,
продуктовый проект, есть ли эпик, стори, спринт.

Читай код до **локализации** — до состояния, когда можешь назвать сервис, файл и
функцию, которых работа касается. Дальше не иди: значения, структуру и алгоритм за
исполнителя не выбирай. Если пользователь сказал «параметры взять с соседнего
топика», твоя работа — назвать этот топик, а не переписать его настройки в тикет.

Если после чтения остаётся вопрос, который меняет постановку («какой интервал по
умолчанию?», «фиксим отображение или причину?»), не угадывай: либо задай его,
либо оставь в описании раздел `## Открытый вопрос` с пометкой «нужно решение».
Второе лучше, когда вопрос не мешает начать работу.

### 2. Определить поля

Различай «Jira-проект» — ключ проекта в трекере — и «продуктовый проект» —
кодовую базу, которой касается работа. Как пользователь называет второе и во что
это превращается в полях, описывает раздел «Продуктовые проекты» профиля.

Скилл заполняет ровно эти поля:

| Поле | Откуда значение |
| --- | --- |
| Jira-проект | раздел «Jira-проект» профиля; пользователь назвал другой ключ — см. шаг 0 |
| Тип | умолчания и список — раздел «Типы задач» |
| Заголовок | по правилам шага 3 |
| Описание | по правилам шага 4 |
| Компонент | умолчание и список — раздел «Компоненты» |
| Лейблы | правила — раздел «Лейблы» |
| Story points | шкала по умолчанию — раздел «Story points» этого файла; уточнения — раздел «Оценка» профиля; нужен id поля из «Кастомных полей»; пользователь назвал число — его |
| Parent | эпик, если дан; иначе эпик стори, если дана стори |
| Связь «split to» | стори, если дана; тип и направление связи — раздел «Связи» |
| Спринт | не ставить; пользователь дал id или точное имя — раздел «Спринты» |

Остальным скилл не управляет: **статус, исполнитель, приоритет, дата, оценка
времени — не его дело.** Тикет создаётся в статусе по умолчанию и там остаётся.
Если пользователь просит назначить исполнителя или сразу перевести статус, скажи,
что это вне скилла, и сделай остальное — руками это одно движение на доске, а
поддержка ещё одного пути в скилле стоит дороже.

### 3. Написать заголовок

Командный формат заголовка — префиксы, их порядок и то, как сокращаются имена
сервисов, — задаёт раздел «Заголовок» профиля. Нет раздела — заголовок без
префиксов. Назвал пользователь своё сокращение — бери его, оно важнее правила
профиля.

Общие правила, не зависящие от профиля:

- Текст — на языке из профиля, одна мысль, без точки в конце. Идентификаторы из
  кода (имена коллекций, эндпоинтов, флагов, статусов) остаются как есть:
  `[back][payments] Возвращать 400 на неизвестный currency_code при оплате`.
- Заголовок называет результат, а не действие агента: «Показывать оплаченные
  баллы в кабинете, когда счёт в статусе Payed», не «Исправить баг с баллами».

### 4. Написать описание

Форма зависит от типа. `Task` и `Bug` описаны каждый в своём файле — читай ровно
один:

| Тип | Форма | Что читать |
| --- | --- | --- |
| `Task` | набор разделов свободный: задача говорит, что нужно сделать и где, а как — решает исполнитель | `references/description-task.md` |
| `Bug` | набор разделов фиксированный: суть, как воспроизвести, ожидаемое и фактическое, окружение, доказательство, механизм | `references/description-bug.md` |
| `Story`, `Research`, `Epic` и остальные типы | короткие формы — ниже в этом файле, reference не нужен | — |

Проверь готовый текст одним вопросом: сможет ли агент в чистом контексте начать
работу, имея только этот тикет? Если для старта нужно знать, от какой ветки
брать базу, или какой файл служит образцом, — это в тикете, а не в чате.

#### Правила текста, общие для всех типов

**Язык — из раздела «Язык» профиля.** Всё тело описания, а не только заголовок:
разделы, абзацы, списки, подписи к ссылкам. Идентификаторы из кода и имена полей
остаются как есть. Самая частая поломка этого скилла — описание на языке
запроса вместо языка профиля, и возникает она, когда запрос сформулирован на
другом языке.

**Футер атрибуции** — последняя строка любого тикета, включая короткие формы.
Перед ним — горизонтальная черта `---`.

**Ключей тикетов в описании нет.** Связь — это поле, а не строка в тексте. Эпик
стоит в `Parent`, стори — в связи «split to», зависимость — стандартной связью
`Blocks`. Строки «Родительская стори: ABC-5512», «Родительский эпик», «Отпилено
от…», «Связано: ABC-5513» не пишутся: на доске их не видно, в фильтры и
зависимости они не попадают, а при смене связи протухают.

Единственное исключение — разделы `## Порядок выполнения` пакета тикетов одной
фичи (см. одноимённый раздел): у очерёдности целиком нет поля в Jira, поэтому
она живёт текстом — поверх связей `Blocks`, а не вместо них.

Заметил связь, которую пользователь не назвал, — скажи о ней в отчёте после
создания и предложи проставить. Вписать ключ в текст вместо связи — это не
компромисс, а потеря: строка выглядит как связь, но ею не является.

Ссылки без ключа (тред, документ, макет, дашборд) остаются в тексте: у них поля
нет вовсе. Каждая с подписью, куда ведёт.

**Чего в описании не бывает:**

- пересказа сессии — «мы обсудили», «как я выяснил выше»: читатель не был в чате;
- ссылок на внутренние документы вместо сути — «по §6.8 плана» не работает,
  тикет должен читаться без документа под рукой;
- планировочного шортката — «вариант A», «Path B» переименовываются в настоящее
  имя случая;
- утверждений сильнее проверенного и чисел без источника: либо измерение с датой,
  либо показание пользователя с пометкой, либо ничего;
- скопированных значений вместо указателя и своего решения в форме требования
  (подробнее — в файле типа);
- оценки объёма в тексте: story points — поле, а не абзац;
- ссылки на сессию Claude Code в любом виде;
- пустых разделов ради полноты;
- картинок: приложить файл через MCP нельзя. Если без скриншота постановка не
  читается, скажи об этом в отчёте и попроси приложить его руками.

#### Story — краткое описание и ссылки

Стори — контейнер: работа описывается в задачах, на которые её режут. Всё, что
нужно, — 2–4 предложения «чего хотим и зачем» плюс набор ссылок с подписью, куда
каждая ведёт: документ, макет, тред, аналитика, соседний тикет.

Плана реализации, файлов, `DOD:` и оценки в стори нет. Не выдумывай разделы: ссылки
— главное содержимое, и лишние заголовки их прячут. Ссылок не дали — стори состоит
из одного абзаца, это нормально.

Одно исключение: стори, создаваемая вместе со своими задачами, получает раздел
`## Порядок выполнения` — после создания всех задач, см. «Пакет тикетов одной
фичи».

#### Research — краткое описание и DOD

Ресёрч заканчивается знанием, а не кодом. Обязательны два блока: исходная картина
в 2–4 предложениях с уже известными фактами (номер заказа, дата, наблюдаемое
поведение) и строка `DOD:` — что должно лежать на выходе.

```markdown
Заказ 21023735 перешёл из «отменён» в «оплачен». Обратный переход по конечному
статусу не предусмотрен, значит либо статус выставлен не тем источником, либо
переход разрешён там, где не должен.

DOD: есть разбор, что происходило с заказом по шагам и кто менял статус;
если нашлась поломка — на исправление заведён тикет.

---

🤖 Generated with Claude Code (Opus 5)
```

Хороший DOD ресёрча называет артефакт («разбор», «сравнение вариантов»,
«заведённый баг»), а не состояние головы («разобрались», «поняли причину»). Объём
DOD задаёт пользователь: ресёрч может заканчиваться одним разбором, без вариантов
решения и без заведённых тикетов. Варианты попадают в DOD, только когда их просили.

Тикет на исправление — это тикет на исправление найденной поломки, а не на
конкретный выбранный вариант: выбор подхода делается при работе над ним. Плана
реализации в ресёрче нет — если бы шаги были известны заранее, это была бы задача.

#### Остальные типы — шаблона нет

У типов вне `Task`, `Bug`, `Story` и `Research` (в командах это обычно `Epic`,
`Design`, `QA`) пиши то, что дал пользователь, на языке профиля и с футером. Не
достраивай структуру и не добавляй разделы «для полноты»: у этих типов формат не
выработан, и придуманный шаблон закрепится как норма, хотя его никто не
согласовывал.

### 5. Создать тикет сразу

Подтверждения не жди: просьба «заведи тикет» — это и есть разрешение. Тикет
обратим — описание правится через `editJiraIssue`, а ненужный тикет вы отменяете
одним движением на доске, — поэтому цена лишнего тикета ниже цены лишнего круга
вопросов.

**Минимальный вход.** У тикета должны быть две вещи: объект работы (что именно
заводим, чиним, меняем) и результат, из которого получается проверяемый `DOD:`.
Если ни того, ни другого нет ни в запросе, ни в контексте сессии — задай один
короткий круг вопросов ровно про эти две вещи. На запрос «создай задачку на новый
топик» без контекста это два вопроса: какой топик и в каком сервисе, и зачем он
нужен.

Спрашивай только про объект и результат. Параметры, значения и способ реализации
не спрашивай никогда — их определяет исполнитель (см. шаг 4). Пустой тикет с одним
разделом «Открытый вопрос» хуже вопроса в чате: он занимает место на доске и всё
равно вернётся к вам.

Спроси до создания и в остальных случаях, когда без ответа тикет получится
неверным, а не неполным:

- названы взаимоисключающие вещи (тип `Bug` для работы, у которой нет дефекта);
- спринт назван так, что его не опознать: «в текущий», «в ближайший» — нужен id
  или точное имя.

Неполнота — не повод останавливаться: неизвестное идёт в `## Открытый вопрос`
внутри тикета, там оно полезнее, чем в чате.

Если пользователь просил показать черновик перед созданием, покажи и жди «да».

Инструменты Atlassian отложенные: пока схема не загружена, вызвать инструмент
нельзя. Собери список по тому, что тикету реально нужно, и загрузи одним вызовом.

| Нужен всегда | `createJiraIssue` |
| --- | --- |
| дана стори | `createIssueLink`; плюс `getJiraIssue`, если эпик не назван |
| создаётся пакет тикетов одной фичи | `createIssueLink` и `editJiraIssue`; плюс `getJiraIssue`, если стори существующая |
| оценка у типа, на чьём экране создания нет поля оценки, или поле не прошло на создании | `editJiraIssue` |
| спринт назван именем, а не id | `searchJiraIssuesUsingJql` |
| просят дописать или переделать тикет | `editJiraIssue`; плюс `getJiraIssue`, если тикет не создан в этой сессии |

Пример для тикета со стори, спринтом и оценкой у баги:

```
ToolSearch("select:mcp__claude_ai_Atlassian__createJiraIssue,mcp__claude_ai_Atlassian__createIssueLink,mcp__claude_ai_Atlassian__editJiraIssue,mcp__claude_ai_Atlassian__searchJiraIssuesUsingJql")
```

Загрузить схему в середине флоу можно, но список лучше собрать заранее: половина
поломок этого скилла — попытка вызвать незагруженный инструмент и молча потерянное
поле.

`cloudId` — из раздела «Сайт» профиля.

Читающих вызовов в этом флоу три, и каждый нужен по своему условию: эпик стори,
id спринта по его имени, текст чужого тикета перед его правкой. Назвал
пользователь эпик и id спринта, а правится тикет из этой же сессии, — не остаётся
ни одного.

Всего остального не проверяй: ни ключ эпика, ни ключ стори, ни метаданные полей,
ни результат создания. Неверный ключ отклонит сам вызов, id полей и типов уже
записаны в профиле. Каждый лишний ответ Jira — это несколько тысяч токенов
служебных данных, и они вытесняют из контекста то, ради чего тикет пишется.

**Если MCP не подключён** (headless- или cron-запуск: MCP с интерактивной
авторизацией там может отсутствовать) — не молчи и не имитируй успех. Отдай
пользователю готовый заголовок, поля списком и полный текст описания, чтобы он
создал тикет руками.

`createJiraIssue` с `contentFormat: "markdown"` (ключ проекта, id полей и их
особенности — из профиля; здесь значения-заглушки):

```json
{
  "cloudId": "<из профиля>",
  "projectKey": "<из профиля>",
  "issueTypeName": "Task",
  "summary": "…",
  "description": "…",
  "parent": "ABC-3480",
  "additional_fields": {
    "components": [{"name": "<из профиля>"}],
    "labels": ["<по правилам профиля>"],
    "<id поля Story Points из профиля>": 2
  }
}
```

Особенности полей на экранах создания (у какого типа поле оценки отсутствует, у
какого подставляется ноль по умолчанию) описывает раздел «Кастомные поля»
профиля — оттуда же видно, что ставится вторым вызовом `editJiraIssue`.

Поведение сервера при отказах и правила правки существующего тикета — в
`references/atlassian-mcp.md`.

### 6. Досоздать связи

Связей у тикета две, и обе задаются только по данным пользователя:

- **Parent — это эпик.** Заполняется у любого типа задачи. Источник по порядку:
  эпик, названный пользователем; если не назван, а стори дана — эпик самой стори.
- **Стори связывается с остальными типами через «split to»:** Story split to
  Task, Bug, Research — с любым типом. `createIssueLink` с типом и направлением
  из раздела «Связи» профиля. Направление важно: обратное прочитается наоборот.

**Стори означает две вещи сразу: связь «split to» и эпик.** Названная стори — это
не только связь. Задача живёт в том же эпике, что и стори, из которой её отпилили,
иначе она выпадает из эпика на доске.

Эпик стори читается до создания, чтобы уехать параметром `parent` в самом вызове
создания, — рецепт вызова и его подводные камни в `references/atlassian-mcp.md`.
Из ответа бери **только** `parent.key`. Текст стори в новый тикет не переписывай
— у задачи свой предмет, и пересказ стори его подменяет.

Эпика у стори нет — новый тикет остаётся без эпика. Спрашивать не о чем.

Ответ на создание содержит поля тикета, и если `parent` в нём пуст, проставь Epic
Link через `editJiraIssue` (id поля — в профиле). Отдельный читающий вызов для
этого не нужен.

Других связей по своей инициативе не создавай. `Blocks`, `Relates` и остальные
типы из профиля появляются, только если пользователь их назвал. Чаще прочих
нужна `Blocks`: «A is blocked by B» — это `inwardIssue` B (тот, кто блокирует) и
`outwardIssue` A. Исключение одно — `Blocks` между задачами пакета одной фичи:
там порядок согласован вместе со списком задач (см. «Пакет тикетов одной фичи»).

Заметил зависимость, которую не называли, — скажи о ней в отчёте и предложи
связь. Молча не создавай: связь меняет вид доски и зависимости, которых никто не
просил. И не подменяй её строкой в описании — см. правила текста.

**Спринт** — политика ниже, доска и id поля в профиле, рецепт поиска id по имени
в `references/atlassian-mcp.md`. Скилл принимает спринт только числовым id или
точным именем. Относительных указаний он не понимает намеренно: «в текущий», «в
следующий», «в ближайший» — это вопрос, а не значение. Определять текущий спринт
по данным трекера ненадёжно, а положить тикет в чужой спринт хуже, чем не
положить никуда: он попадёт в чей-то отчёт о выполненном. Про спринт не просили
— поле не заполняется: тикет положат на груминге.

Если в проекте нет подзадач (см. «Jira-проект» профиля), просьбу «заведи
подзадачу под ABC-5505» выполняй как обычную задачу, связанную со стори через
«split to», либо с эпиком в `Parent`, и скажи пользователю, что подзадачей это
не стало.

### 7. Отчитаться

Дай ссылку `<URL сайта из профиля>/browse/<KEY>`, перечисли поля (тип,
компонент, лейблы, оценка с обоснованием в одну строку, parent, связи, спринт) и
покажи полный текст описания в чате.

Текст показывается именно после создания: тикет уже есть, и чтение здесь нужно не
для разрешения, а чтобы вы поймали неверную формулировку и сказали, что
поправить. Правка идёт через `editJiraIssue`.

Разделяй в отчёте подтверждённое и переданное. Ответ на создание содержит не все
поля: `parent`, оценка и спринт в него не входят. Про них честная формулировка —
«передан `parent` ABC-3480, подтверждение не запрашивал». Не выдавай отправленное
значение за проставленное.

Если Jira отклонила поле, скажи об этом прямо, а не молча опусти.

## Пакет тикетов одной фичи

Пакет — это несколько тикетов одной фичи за один заход: стори плюс задачи, на
которые она разрезана, либо перечисленные пользователем связанные задачи. У
пакета есть порядок выполнения, и он фиксируется в трёх местах: связями `Blocks`
между задачами, разделом `## Порядок выполнения` в стори и таким же разделом в
каждой задаче. Одиночного тикета всё это не касается.

Порядок определяется до создания, вместе с составом. Когда состав согласуется с
пользователем, покажи очерёдность прямо в списке — отдельного круга вопросов она
не стоит. Когда пользователь сам перечислил задачи, бери порядок из перечисления
или из названных зависимостей. Задачи, не зависящие друг от друга, помечай
параллельными — им один шаг на всех. Если очерёдности между задачами нет вовсе,
пакетных разделов и связей нет тоже: не выдумывай зависимость ради формы.

Создавай задачи в порядке выполнения: к моменту создания каждой следующей ключи
её предшественников уже существуют, и описание пишется сразу с ними, без второго
прохода по созданным тикетам.

**`Blocks` между задачами.** Каждая зависимость «сначала A, потом B» — связь
`Blocks`: `inwardIssue` — предшественник A, `outwardIssue` — зависимая B.
Ставится сразу после создания зависимой задачи, вместе со «split to».
Параллельные задачи между собой не связываются.

**Раздел в задаче** — `## Порядок выполнения`, сразу после строки `DOD:`. Одна-две
строки: номер шага, предшественники с ключом и коротким названием, параллельные
соседи. Форма — в `references/description-task.md`.

**Раздел в стори** — `## Порядок выполнения`, последний перед футером:
нумерованный список шагов, параллельные задачи в одном пункте.

```markdown
## Порядок выполнения

1. ABC-5601 — топик в двух регионах
2. ABC-5602 — продюсер изменений расписания; параллельно ABC-5603 — метрики топика
3. ABC-5604 — читатель во втором регионе
```

При создании стори ключей задач ещё нет, поэтому раздел добавляется через
`editJiraIssue` после создания всех задач. Текст стори из этой сессии у тебя в
контексте; у существующей стори сначала прочитай описание, как при любой правке
чужого тикета (см. «Границы»). Подтверждения на эту правку не жди: состав и
порядок согласованы до создания пакета.

Ключи тикетов в этих разделах — намеренное исключение из правила «связь — это
поле»: у очерёдности целиком нет поля в Jira, связи `Blocks` дают только парные
зависимости. Разделы дополняют связи, а не заменяют их: зависимость без связи
`Blocks` не существует, каким бы текстом она ни была описана.

## Story points

Оценка ставится, когда в разделе «Кастомные поля» профиля есть id поля Story
Points. Нет id — ставить некуда, и оценка не ставится вовсе.

Шкала по умолчанию встроена в скилл — таблица ниже. Раздел «Оценка» профиля —
командное уточнение: свои примеры, другие типы задач с оценкой, другая шкала.
В той части, которую он задаёт, профиль выигрывает у умолчания.

По умолчанию оценка есть у `Task` и `Bug`. У `Story`, `Epic` и остальных типов
поле остаётся пустым: это контейнеры, их объём складывается из оценок вложенных
задач, а не проставляется сверху.

| Баллы | Объём работы |
| --- | --- |
| 0 | работа не требуется: закрывается за минуту; ставится осознанно, а не как «не оценил» |
| 1 | маленькая задача или простой баг |
| 2 | подправить существующее поведение или небольшой рефакторинг |
| 3 | новая функциональность, не требующая много работы |
| 5 | нормальная задача, требующая вдумчивой работы |
| 8 | большая и сложная задача на весь спринт: часть моментов неизвестна, нужен ресёрч |
| 13 | сигнальная: в спринт брать нельзя — сначала проработать и, скорее всего, разбить |
| 21 | сигнальная: сложность оценить невозможно — сперва ресёрч и разбиение |

Оценивай сам и назови обоснование одной строкой в отчёте после создания.
Пользователь поправит число, если не согласен.

Сигнальная оценка (13 и 21, если профиль не задал иных) — это не оценка, а
сигнал. Тикет всё равно заводи: он и есть место, где работа названа.
Вместе с ним предложи разбиение — стори плюс задачи, связанные с ней через
«split to», — и не создавай эти задачи сам, пока состав не согласован. Дели по
флоу или по звеньям, а не по слоям кода, чтобы каждая задача выкатывалась
самостоятельно. Согласованный набор создавай как пакет — с порядком выполнения и
связями `Blocks` (см. «Пакет тикетов одной фичи»).

Оценивай объём работы, а не свою скорость. Задача на 8 не становится задачей на
2 от того, что код пишет агент: неизвестные моменты и нужда в ресёрче остаются, а
именно они определяют балл.

## Футер атрибуции

Описание заканчивается горизонтальной чертой и строкой атрибуции:

```markdown
---

🤖 Generated with <инструмент> (<модель>)
```

Черта обязательна: она отделяет подпись от последнего раздела, иначе футер
читается как часть его текста.

Инструмент — тот, в котором ты работаешь (`Claude Code`). Модель — имя модели из
твоего собственного контекста, без суффикса про размер окна: `Opus 5`,
`Fable 5`, `Sonnet 5`. Пример: `🤖 Generated with Claude Code (Opus 5)`.

Читатель тикета должен видеть, чем именно написан текст: у моделей разное
качество постановки, и это влияет на то, насколько тикету верят.

## Границы

- Один вызов — один тикет. Исключения два. Пользователь сам перечислил несколько
  тикетов («заведи три таски: топик, метрики, документация») — заводи все, каждый
  по своим правилам, и отчитайся списком. Пользователь просит разбить объём, а
  состав задач определяешь ты — сначала согласуй список, потом создавай. В обоих
  случаях тикеты одной фичи с очерёдностью — это пакет: порядок выполнения и
  связи `Blocks` по разделу «Пакет тикетов одной фичи».
- Тикет создаётся в статусе по умолчанию и по статусам не двигается.
- Существующий тикет скилл правит только по просьбе: «допиши в ABC-1234»,
  «переделай описание». Порядок: взять текущий текст → собрать новую версию
  целиком → показать её пользователю → дождаться «да» → `editJiraIssue`.

  Откуда берётся текущий текст, зависит от того, чей это тикет. Свой, созданный в
  этой же сессии, — текст у тебя в контексте, ты его писал, читать не надо. Чужой
  или из прошлой сессии — `getJiraIssue` с `fields: ["summary","description"]` и
  `responseContentFormat: "markdown"` обязателен: `description` перезаписывается
  целиком, и без чтения ты не дописываешь, а стираешь.

  Сам, по своей инициативе, чужие тикеты не трогай.

## Файлы скилла и данные

Конфигурация — вне плагина, в `${CLAUDE_PLUGIN_DATA}`: `config.md` (маппинг
«репозиторий → профиль») и `profiles/*.md`. Формат профиля — в
`references/profile-template.md`; новый профиль создаёт команда
`/jira-ticket-creator:setup`.

Файлы reference самодостаточны: для одного тикета читается ровно один из первых
двух, и только когда тип — `Task` или `Bug`.

- `references/description-task.md` — `Task`: принцип «что и где, а как решает
  исполнитель», каркас, наполнение шага, слой для человека и `DOD:`, порядок
  выполнения в пакете, разделы по необходимости, почему значения не копируются,
  два разобранных примера.
- `references/description-bug.md` — `Bug`: фиксированный набор разделов, два
  режима (разобранный дефект и наблюдение), правила для воспроизведения,
  окружения, доказательства, механизма и гипотез, пример.
- `references/atlassian-mcp.md` — поведение Atlassian MCP: чтение эпика стори,
  поиск id спринта по имени, чем отвечает создание, правка существующего
  тикета, отказы Jira и WAF. Читать, когда нужен спринт, правка чужого тикета
  или когда вызов упал.
- `references/profile-template.md` — формат профиля: обязательные и
  необязательные разделы. Читать только в setup и при правке профиля.
