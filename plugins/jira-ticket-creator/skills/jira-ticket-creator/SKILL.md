# Тикет в Jira

Скилл создаёт тикет: поля по командным умолчаниям плюс описание, по которому
исполнитель начинает работу, не имея доступа к этому чату.

Главная ценность здесь — описание, а не поля. Тикет живёт дольше сессии: его
читают через месяц, по нему работает другой человек или агент в чистом контексте.
Поэтому описание не пересказывает разговор, а заменяет его.

## Правило первое: сначала факты, потом текст

Каждый факт в описании проверен в первоисточнике до того, как попал в текст:

- путь к файлу, имя метода, текущий код — открыты в репозитории;
- число («7 срабатываний в сутки», «14 из 191 счёта за 30 дней») — снято
  измерением, и в тексте стоит рядом с датой измерения;
- ключ Jira в ссылках — назван пользователем или найден в коде и коммитах, а не
  собран по памяти; выдумывать ключи нельзя, но и проверять их запросом не нужно:
  неверный ключ отклонит сам вызов создания связи;
- ссылка на тред или заказ — дана пользователем или найдена, не собрана из
  догадки.

Непроверенный факт не пишется вообще. Вместо него — либо явная строка «нужно
проверить: …», либо вопрос пользователю. Ошибочный путь к файлу в тикете дороже
отсутствующего: он уводит исполнителя в неверное место с полной уверенностью.

Правило касается фактов, которые ты утверждаешь, и только их. Ненайденное решение
— не пробел: задача говорит, что нужно сделать, а как — решает исполнитель (см.
шаг 4). Не путай «не проверил» с «не моё решение».

Когда пользователь просит тикет «по тому, что мы только что обсуждали», источник
фактов — эта сессия, но пути, имена и числа всё равно перечитываются в коде и в
данных. В сессии они могли измениться или быть названы приблизительно.

## Шаги

### 1. Собрать факты

Определи по запросу пользователя: тип работы, затронутый репозиторий и файлы,
проект (my-orders / my-flight-status / другое), есть ли эпик, стори, спринт,
исполнитель.

Читай код до **локализации** — до состояния, когда можешь назвать сервис, файл и
функцию, которых работа касается. Дальше не иди: значения, структуру и алгоритм за
исполнителя не выбирай. Если пользователь сказал «параметры взять с соседнего
топика», твоя работа — назвать этот топик, а не переписать его настройки в тикет.

Если после чтения остаётся вопрос, который меняет постановку («какой интервал по
умолчанию?», «фиксим отображение или причину?»), не угадывай: либо задай его,
либо оставь в описании раздел `## Открытый вопрос` с пометкой «нужно решение».
Второе лучше, когда вопрос не мешает начать работу.

### 2. Определить поля

| Поле | Умолчание | Когда меняется |
| --- | --- | --- |
| Проект | `PX` | пользователь назвал другой |
| Тип | `Task`, для дефекта `Bug` | пользователь назвал: `Story`, `Epic`, `Design`, `QA`, `Research` |
| Статус | `Inbox` (статус создания) | пользователь попросил другой — см. reference по транзишенам |
| Компонент | `Backend` | работа не бэкендовая: `iOS`, `Android`, `WEB`, `Design`, `QA`, `Launch`, `Backend Sharp` |
| Лейблы | тип работы + проект — см. ниже | — |
| Story points | оценка по шкале команды — см. ниже; только для `Task` и `Bug` | пользователь назвал число |
| Assignee | не назначать | пользователь назвал исполнителя |
| Parent | эпик, если дан | — |
| Спринт | не ставить | пользователь попросил спринт |
| Приоритет | не ставить (`Medium (P2)` по умолчанию Jira) | пользователь назвал |

Лейблы: ровно один по типу работы плюс проектные по числу затронутых проектов.

- Тип работы — всегда один: `product` — текущая продуктовая задача;
  `product-debt` — продуктовая задача на потом (например, поменять поведение);
  `tech-debt` — технический долг; `bug` — дефект (у типа `Bug` лейбл `bug`
  всегда).
- Проект: `my-orders` или `my-flight-status`. Правка в двух проектах — оба
  лейбла: тикет должен находиться в выборке по каждому затронутому проекту.
  Заголовок в этом случае, наоборот, теряет второй префикс — там задача выбрать
  одно имя, здесь ограничения на число нет.
- Если работа вне этих двух проектов (например, oncall-bot или ota-mordor),
  проектного лейбла нет — не подгоняй задачу под существующий лейбл.

### 3. Написать заголовок

Формат: `[префикс] Русский текст`.

Первый префикс — область. Для бэкенда это всегда `[back]`.

Второй префикс зависит от того, насколько широко расходится правка:

| Охват правки | Второй префикс | Пример |
| --- | --- | --- |
| один сервис | имя этого сервиса | `[back][flight-status]` |
| несколько сервисов одного проекта | имя проекта | `[back][mfs]` |
| несколько проектов | нет второго префикса | `[back]` |

Короткое имя берётся то, которым проект называют в команде (`mfs` —
my-flight-status, `mordor` — монолит ota-mordor). Если устоявшегося сокращения
нет, пиши имя каталога сервиса или проекта.

- Текст — на русском, одна мысль, без точки в конце. Идентификаторы из кода
  (имена коллекций, эндпоинтов, флагов, статусов) остаются как есть:
  `[back][mfs] Копировать flight_schedule_changes при импорте подписки prod→dev`.
- Заголовок называет результат, а не действие агента: «Показывать оплаченные
  баллы в МК, когда счёт в статусе Payed», не «Исправить баг с баллами».

### 4. Написать описание

Форма зависит от типа. Сначала прочитай `references/description-common.md` — там
общее для всех типов, — затем файл своего типа:

| Тип | Форма | Что читать |
| --- | --- | --- |
| `Task` | набор разделов свободный: задача говорит, что нужно сделать и где, а как — решает исполнитель | `references/description-task.md` |
| `Bug` | набор разделов фиксированный: суть, как воспроизвести, ожидаемое и фактическое, окружение, доказательство, механизм | `references/description-bug.md` |
| `Story` | свободная форма: краткое описание плюс набор ссылок | `description-common.md` |
| `Research` | краткое описание плюс строка `DOD:` — что должно быть на выходе | `description-common.md` |
| `Epic`, `Design`, `QA` | шаблона нет: пиши то, что дал пользователь | — |

Почему у типов разные правила. У задачи набор разделов диктует содержание: есть что
сказать про порядок работ — есть раздел, нет — нет. У дефекта наоборот: набор
фиксирован, потому что дефект должен воспроизвести другой человек, а воспроизведение
разваливается от любой недостающей детали — версии, конфига, состояния данных.

Четыре вещи есть у любого типа: вводный абзац для человека, строка `DOD:`,
`## База для работы`, футер атрибуции.

Не навязывай структуру там, где её нет. Стори режется на задачи, и детали живут в
них; пустые разделы в стори мешают увидеть ссылки, ради которых её и завели.

Проверь готовый текст одним вопросом: сможет ли агент в чистом контексте начать
работу, имея только этот тикет? Если для старта нужно знать, от какой ветки
резать, или какой файл служит образцом, — это в тикете, а не в чате.

### 5. Создать тикет сразу

Подтверждения не жди: просьба «заведи тикет» — это и есть разрешение. Тикет
обратим — описание правится через `editJiraIssue`, ненужный тикет уходит в
`Closed` (в PX это «отменён»), — поэтому цена лишнего тикета ниже цены лишнего
круга вопросов.

Спроси до создания только тогда, когда без ответа тикет получится неверным, а не
неполным:

- пользователь просит следующий спринт, а будущего спринта на доске нет;
- названы взаимоисключающие вещи (тип `Bug` для работы, у которой нет дефекта);
- назван исполнитель, и поиск даёт несколько человек с таким именем.

Неполнота — не повод останавливаться: неизвестное идёт в `## Открытый вопрос`
внутри тикета, там оно полезнее, чем в чате.

Если пользователь просил показать черновик перед созданием, покажи и жди «да».

Инструменты Atlassian отложенные — загрузи ровно те, которыми будешь писать:

```
ToolSearch("select:mcp__claude_ai_Atlassian__createJiraIssue,mcp__claude_ai_Atlassian__createIssueLink,mcp__claude_ai_Atlassian__editJiraIssue")
```

`cloudId` для aviasales.atlassian.net — `b7cc35a5-077d-4e65-890a-2134bf111631`.

Читающих вызовов в этом флоу нет. Не проверяй заранее ни ключ эпика, ни ключ
стори, ни метаданные полей: неверный ключ отклонит сам вызов создания, а id полей
и типов уже записаны в reference. Каждый ответ Jira — это несколько тысяч токенов
служебных данных, и они вытесняют из контекста то, ради чего тикет пишется.

`createJiraIssue` с `contentFormat: "markdown"`:

```json
{
  "cloudId": "b7cc35a5-077d-4e65-890a-2134bf111631",
  "projectKey": "PX",
  "issueTypeName": "Task",
  "summary": "[back][mfs] …",
  "description": "…",
  "parent": "PX-3480",
  "additional_fields": {
    "components": [{"name": "Backend"}],
    "labels": ["my-flight-status", "tech-debt"],
    "customfield_10004": 2
  }
}
```

`customfield_10004` — Story Points. Остальные id полей, спринт, транзишены
статусов и обходные пути при отказах — в `references/fields-and-transitions.md`.

### 6. Досоздать связи

Связей у тикета две, и обе задаются только по данным пользователя:

- **Parent — это эпик.** Заполняется у любого типа задачи. Передан параметром
  `parent` при создании; ответ на создание содержит поля тикета, и если `parent` в
  нём пуст, проставь Epic Link через `editJiraIssue` (см. reference). Отдельный
  читающий вызов для этого не нужен.
- **Стори связывается с остальными типами через «split to»:** Story split to
  Task. `createIssueLink` с типом `Work item split`, где `inwardIssue` — стори,
  `outwardIssue` — новый тикет. Направление именно такое: обратное прочитается
  наоборот.

Других связей по своей инициативе не создавай. `Blocks`, `Relates`,
`Problem/Incident`, `Duplicate` появляются, только если пользователь их назвал.
Соседний тикет, про который полезно знать, упоминается в тексте описания — этого
достаточно, а лишняя связь меняет вид доски и зависимости, которых никто не
просил.

**Спринт** и **статус, отличный от Inbox** — по reference.

### 7. Отчитаться

Дай ссылку `https://aviasales.atlassian.net/browse/<KEY>`, перечисли, что
фактически проставилось (тип, статус, компонент, лейблы, оценка с обоснованием в
одну строку, parent, связи, спринт), и покажи полный текст описания в чате.

Текст показывается именно после создания: тикет уже есть, и чтение здесь нужно не
для разрешения, а чтобы вы поймали неверную формулировку и сказали, что
поправить. Правка идёт через `editJiraIssue`.

Данные бери из ответа на создание, а не из нового запроса. Если Jira отклонила
поле, скажи об этом прямо, а не молча опусти.

## Story points

Оценка ставится **только у типов `Task` и `Bug`**. У `Story`, `Epic`, `Design`,
`QA` и `Research` поле остаётся пустым: стори и эпик — это контейнеры, их объём
складывается из оценок вложенных задач, а не проставляется сверху.

Оценивай сам и назови обоснование одной строкой в отчёте после создания.
Пользователь поправит число, если не согласен.

Шкала команды — [«Как оценивать задачи»](https://aviasales.atlassian.net/wiki/spaces/PREM/pages/3752591422):

| Баллы | Объём работы | Примеры из статьи |
| --- | --- | --- |
| 0 | работа не требуется: задача уже в тестировании или закрывается за минуту | выключить флаг в конфиге, нажать merge, поправить опечатку в сообщении логгера |
| 1 | маленькая задача или простой баг | изменить текст на кнопке, починить сломанный unit-тест, простая миграция с добавлением колонки |
| 2 | подправить работу кода или небольшой рефакторинг | обработка кода ошибки от партнёра, прокинуть одно простое поле в API, простые prometheus-метрики, документация в Confluence |
| 3 | новая функциональность, не требующая много работы | добавить эндпоинт, добавить новый тип сущности с интеграционными тестами, миграция с несколькими таблицами и индексами |
| 5 | нормальная задача, требующая вдумчивой работы | реализовать бизнес-логику фичи с покрытием unit- и интеграционными тестами |
| 8 | большая и сложная задача на весь спринт: часть моментов неизвестна, нужен ресёрч | новый сервис с базовой логикой и тестами |
| 13 | в спринт брать нельзя — сначала проработать и, скорее всего, разбить | новый сервис с функционалом, тестами, конфигами и всеми метриками |
| 21 | сложность оценить невозможно: сперва ресёрч и разбиение | «прикрутить Stripe» |

Оценка 13 или 21 — это не оценка, а сигнал. Ставь её только вместе с
предложением разбить работу: стори плюс задачи, связанные с ней через
«split from». Дели по флоу или по звеньям, а не по слоям кода, чтобы каждая
задача выкатывалась самостоятельно.

Ноль ставится осознанно и означает «работы нет». Не используй его как «не
оценил»: пустое поле честнее.

Оценивай объём работы, а не свою скорость. Задача на 8 не становится задачей на
2 от того, что код пишет агент: неизвестные моменты и нужда в ресёрче остаются, а
именно они определяют балл.

## Футер атрибуции

Описание заканчивается строкой:

```
🤖 Generated with <инструмент> (<модель>)
```

Инструмент — тот, в котором ты работаешь (`Claude Code`). Модель — имя модели из
твоего собственного контекста, без суффикса про размер окна: `Opus 5`,
`Fable 5`, `Sonnet 5`. Пример: `🤖 Generated with Claude Code (Opus 5)`.

Читатель тикета должен видеть, чем именно написан текст: у моделей разное
качество постановки, и это влияет на то, насколько тикету верят.

## Границы

- Один вызов — один тикет, кроме явной просьбы разбить объём на несколько.
  Тогда сначала согласуй разбиение списком, потом создавай.
- Тикет не двигается по статусам сверх запрошенного при создании.
- Существующий тикет этот скилл не редактирует. Если пользователь просит
  дописать или переоформить уже созданный тикет, это `editJiraIssue` по тому же
  формату описания — но подтверждение перед перезаписью чужого текста
  обязательно.

## Файлы скилла

- `references/description-common.md` — общее для всех типов: на какой практике
  стоит каждый раздел, слой для человека, `DOD:`, база для работы, разделы по
  необходимости, блок связей, антипаттерны, а также правила для `Story`,
  `Research` и остальных типов. Читать всегда перед написанием текста.
- `references/description-task.md` — `Task`: принцип «что и где, а как — решает
  исполнитель», наполнение шага, почему значения не копируются, почему пример не
  становится требованием, два примера.
- `references/description-bug.md` — `Bug`: фиксированный набор разделов, правила
  для воспроизведения, окружения, доказательства, механизма и гипотез, пример.
- `references/fields-and-transitions.md` — id полей, типы задач, спринты,
  цепочка транзишенов статусов, поведение при отказах Jira. Читать, когда нужен
  спринт, нестандартный статус или когда поле не проставилось.
