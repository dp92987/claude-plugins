# Тикет в Jira

Скилл создаёт тикет: поля по командным умолчаниям плюс описание, по которому
исполнитель начинает работу, не имея доступа к этому чату.

Главная ценность здесь — описание, а не поля. Тикет живёт дольше сессии: его
читают через месяц, по нему работает другой человек или агент в чистом контексте.
Поэтому описание не пересказывает разговор, а заменяет его.

## Правило первое: сначала факты, потом текст

Каждый факт в описании проверен в первоисточнике до того, как попал в текст:

- путь к файлу, имя метода, текущий код — открыты в репозитории;
- число («7 срабатываний в сутки», «14 из 191 счёта за 30 дней») — снято
  измерением, и в тексте стоит рядом с датой измерения;
- ключ Jira в ссылках — проверен через `getJiraIssue`;
- ссылка на тред или заказ — дана пользователем или найдена, не собрана из
  догадки.

Непроверенный факт не пишется вообще. Вместо него — либо явная строка «нужно
проверить: …», либо вопрос пользователю. Ошибочный путь к файлу в тикете дороже
отсутствующего: он уводит исполнителя в неверное место с полной уверенностью.

Когда пользователь просит тикет «по тому, что мы только что обсуждали», источник
фактов — эта сессия, но пути, имена и числа всё равно перечитываются в коде и в
данных. В сессии они могли измениться или быть названы приблизительно.

## Шаги

### 1. Собрать факты

Определи по запросу пользователя: тип работы, затронутый репозиторий и файлы,
проект (my-orders / my-flight-status / другое), есть ли эпик, стори, спринт,
исполнитель. Дочитай код и данные до состояния, при котором можешь назвать
конкретные файлы и методы.

Если после чтения остаётся вопрос, который меняет постановку («какой интервал по
умолчанию?», «фиксим отображение или причину?»), не угадывай: либо задай его,
либо оставь в описании раздел `## Открытый вопрос` с пометкой «нужно решение».
Второе лучше, когда вопрос не мешает начать работу.

### 2. Определить поля

| Поле | Умолчание | Когда меняется |
| --- | --- | --- |
| Проект | `PX` | пользователь назвал другой |
| Тип | `Task`, для дефекта `Bug` | пользователь назвал: `Story`, `Epic`, `Design`, `QA`, `Research` |
| Статус | `Inbox` (статус создания) | пользователь попросил другой — см. reference по транзишенам |
| Компонент | `Backend` | работа не бэкендовая: `iOS`, `Android`, `WEB`, `Design`, `QA`, `Launch`, `Backend Sharp` |
| Лейблы | тип работы + проект — см. ниже | — |
| Story points | оценка по фибоначчи — см. ниже | пользователь назвал число |
| Assignee | не назначать | пользователь назвал исполнителя |
| Parent | эпик, если дан | — |
| Спринт | не ставить | пользователь попросил спринт |
| Приоритет | не ставить (`Medium (P2)` по умолчанию Jira) | пользователь назвал |

Лейблы ставятся парой: один по типу работы плюс один по проекту.

- Тип работы: `product` — текущая продуктовая задача; `product-debt` —
  продуктовая задача на потом (например, поменять поведение); `tech-debt` —
  технический долг; `bug` — дефект (у типа `Bug` лейбл `bug` всегда).
- Проект: `my-orders` или `my-flight-status`. Если работа вне этих двух проектов
  (например, oncall-bot или ota-mordor), проектного лейбла нет — не подгоняй
  задачу под существующий лейбл.

### 3. Написать заголовок

Формат: `[префикс] Русский текст`.

- Префикс области обязателен: `[back]` для бэкенда, по аналогии для остальных
  компонентов.
- Второй префикс добавляется, когда полезно назвать кодовую базу или сервис:
  `[back][mfs]`, `[back][mordor]`. Используй уже существующий префикс — проверь
  поиском по недавним тикетам, а не изобретай новый.
- Текст — на русском, одна мысль, без точки в конце. Идентификаторы из кода
  (имена коллекций, эндпоинтов, флагов, статусов) остаются как есть:
  `[back][mfs] Копировать flight_schedule_changes при импорте подписки prod→dev`.
- Заголовок называет результат, а не действие агента: «Показывать оплаченные
  баллы в МК, когда счёт в статусе Payed», не «Исправить баг с баллами».

### 4. Написать описание

Полный формат, словарь разделов и разобранные примеры — в
`references/description-format.md`. Прочитай его перед тем, как писать текст:
там же указано, какие разделы обязательны, а какие появляются по необходимости.

Каркас: строка со ссылками на источник (если есть) → вводный абзац для человека
без заголовка → строка `DOD:` → `## Что нужно реализовать` с нумерованными
подразделами → разделы-обоснования по необходимости → блок связей после `---` →
футер атрибуции.

Проверь готовый текст одним вопросом: сможет ли агент в чистом контексте начать
работу, имея только этот тикет? Если для старта нужно знать, от какой ветки
резать, или какой файл служит образцом, — это в тикете, а не в чате.

### 5. Показать превью и дождаться подтверждения

Покажи в чате: заголовок, все поля списком, оценку с обоснованием в одну строку,
полный текст описания. Дождись явного «да».

Тикет создаётся под аккаунтом пользователя и виден команде, поэтому по умолчанию
подтверждение обязательно. Пропусти его, только если пользователь заранее сказал
создавать без подтверждения.

### 6. Создать тикет

Инструменты Atlassian отложенные — сначала загрузи схемы:

```
ToolSearch("select:mcp__claude_ai_Atlassian__createJiraIssue,mcp__claude_ai_Atlassian__editJiraIssue,mcp__claude_ai_Atlassian__createIssueLink,mcp__claude_ai_Atlassian__getJiraIssue,mcp__claude_ai_Atlassian__searchJiraIssuesUsingJql")
```

`cloudId` для aviasales.atlassian.net — `b7cc35a5-077d-4e65-890a-2134bf111631`.
Если сайт другой, возьми его через `getAccessibleAtlassianResources`.

`createJiraIssue` с `contentFormat: "markdown"`:

```json
{
  "cloudId": "b7cc35a5-077d-4e65-890a-2134bf111631",
  "projectKey": "PX",
  "issueTypeName": "Task",
  "summary": "[back][mfs] …",
  "description": "…",
  "parent": "PX-3480",
  "additional_fields": {
    "components": [{"name": "Backend"}],
    "labels": ["my-flight-status", "tech-debt"],
    "customfield_10004": 2
  }
}
```

`customfield_10004` — Story Points. Остальные id полей, спринт, транзишены
статусов и обходные пути при отказах — в `references/fields-and-transitions.md`.

### 7. Досоздать связи

- **Эпик** передан параметром `parent` при создании. Проверь через
  `getJiraIssue`, что поле проставилось; если нет — reference описывает
  запасной путь через Epic Link.
- **Стори** (когда пользователь её дал) связывается как «split from»:
  `createIssueLink` с типом `Work item split`, где `inwardIssue` — стори,
  `outwardIssue` — новый тикет. Направление именно такое: обратное даст «split
  to» и связь прочитается наоборот.
- **Спринт** и **статус, отличный от Inbox** — по reference.

### 8. Отчитаться

Дай ссылку `https://aviasales.atlassian.net/browse/<KEY>` и перечисли, что
фактически проставилось: тип, статус, компонент, лейблы, оценка, parent, связи,
спринт. Если что-то не проставилось (Jira отклонила поле), скажи об этом прямо,
а не молча опусти.

## Story points

Оценивай сам по шкале 1, 2, 3, 5, 8 и покажи обоснование в одну строку в превью.
Пользователь поправит число, если не согласен.

Якоря шкалы — реальные тикеты, а не абстрактные «часы»:

| Оценка | Объём | Якорь |
| --- | --- | --- |
| 1 | правка в одном файле по готовому образцу рядом, тесты дополняются | PX-5487: дописать `typeof(ApiErrorResponseModel)` в атрибуты swagger |
| 2 | одна фича в 2–3 звеньях существующего флоу, образец есть | PX-5505: `flight_schedule_changes` в экспорт, прокси и импорт подписки |
| 3 | новый эндпоинт или компонент со спекой, портом логики и юнит-тестами | PX-5499: диагностический health-report эндпоинт |
| 5 | новая подсистема или флоу: несколько сервисов, конфиг, миграции, нужен план перед кодом | — |
| 8 | верхняя граница; обычно признак, что задачу пора делить | — |

Оценка выше 8 не ставится. Если объём больше — предложи разбить: стори плюс
задачи, связанные с ней через «split from». Дели по флоу или по звеньям, а не по
слоям кода, чтобы каждая задача выкатывалась самостоятельно.

## Футер атрибуции

Описание заканчивается строкой:

```
🤖 Generated with <инструмент> (<модель>)
```

Инструмент — тот, в котором ты работаешь (`Claude Code`). Модель — имя модели из
твоего собственного контекста, без суффикса про размер окна: `Opus 5`,
`Fable 5`, `Sonnet 5`. Пример: `🤖 Generated with Claude Code (Opus 5)`.

Читатель тикета должен видеть, чем именно написан текст: у моделей разное
качество постановки, и это влияет на то, насколько тикету верят.

## Границы

- Один вызов — один тикет, кроме явной просьбы разбить объём на несколько.
  Тогда сначала согласуй разбиение списком, потом создавай.
- Тикет не двигается по статусам сверх запрошенного при создании.
- Существующий тикет этот скилл не редактирует. Если пользователь просит
  дописать или переоформить уже созданный тикет, это `editJiraIssue` по тому же
  формату описания — но подтверждение перед перезаписью чужого текста
  обязательно.

## Файлы скилла

- `references/description-format.md` — формат описания, словарь разделов,
  разобранные примеры. Читать перед написанием текста.
- `references/fields-and-transitions.md` — id полей, типы задач, спринты,
  цепочка транзишенов статусов, обходные пути при отказах Jira. Читать, когда
  нужен спринт, нестандартный статус или когда поле не проставилось.
