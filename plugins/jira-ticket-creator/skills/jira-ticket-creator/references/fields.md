# Поля и спринты (проект PX, aviasales.atlassian.net)

Значения ниже сняты с живого проекта 13.08.2026. Этот файл — замена читающим
вызовам: id полей, типов и связей берутся отсюда, а не запросом метаданных.

Если Jira отвечает «field cannot be set», не тяни метаданные экрана создания:
ответ `getJiraIssueTypeMetaWithFields` по проекту PX — это около 240 тысяч знаков,
он вытеснит из контекста саму задачу. Создай тикет без спорного поля, скажи
пользователю, какое поле Jira отклонила, и предложи поставить его руками.

`cloudId` = `b7cc35a5-077d-4e65-890a-2134bf111631` (сайт `aviasales.atlassian.net`,
проект `PX` = «Passenger Experience», id `12416`).

| `Bug` | 1 | дефект |
| `Story` | 10001 | постановка, которую дальше режут на задачи |
| `Epic` | 10000 | уровень выше задачи (`hierarchyLevel: 1`) |
| `Design` | 10363 | дизайн |

## Кастомные поля

| Поле | id | Значение при создании |
| --- | --- | --- |
| Story Points | `customfield_10004` | число по шкале команды; только у `Task` и `Bug` — см. ниже |
| Sprint | `customfield_10006` | id спринта числом |
| Epic Link | `customfield_10007` | ключ эпика строкой (`"PX-3480"`) |
| Parent | `parent` | ключ эпика (отдельный параметр `createJiraIssue`) |

**Story Points и тип задачи.** На экране создания `Task` поле есть, с умолчанием
`0`: не передав оценку, получишь ноль, а не пусто. На экране создания `Bug` поля
**нет вовсе** (проверено по метаданным PX 13.08.2026: у `Task` 32 поля и
`customfield_10004` среди них, у `Bug` 30 полей и его нет). Оценку баги ставь
вторым вызовом:

```json
{"cloudId": "…", "issueIdOrKey": "PX-XXXX", "fields": {"customfield_10004": 2}}
```

**Эпик.** Передавай `parent` при создании. У существующих тикетов заполнены оба
поля (`parent` и Epic Link с одним и тем же ключом) — Jira синхронизирует их
сама. Если в ответе на создание `parent` пуст, проставь Epic Link вручную:

```json
{"cloudId": "…", "issueIdOrKey": "PX-XXXX", "fields": {"customfield_10007": "PX-3480"}}
```

**Подзадач в PX нет.** Все семь типов — верхнего уровня (`subtask: false`),
иерархию даёт `parent` у эпика и связь «split to» у стори.

## Спринты

`customfield_10006`, доска PX — id 420. Значение — числовой id спринта:
`{"customfield_10006": 29280}`.

Скилл принимает спринт только двумя способами:

1. **Числовой id** — `{"customfield_10006": 29280}`. Запроса нет.
2. **Точное имя** — «PX Sprint 08.12 — 08.25». Один читающий вызов, чтобы
   превратить имя в id: поле принимает число, а не строку.

Относительных указаний скилл не понимает намеренно. «В текущий», «в следующий»,
«в ближайший» — это вопрос, а не значение: спроси id или точное имя. Определять
текущий спринт по данным трекера ненадёжно, а положить тикет в чужой спринт хуже,
чем не положить никуда: он попадёт в чей-то отчёт о выполненном.

Про спринт не просили — поле не заполняется. Тикет создаётся вне спринта, его
положат на груминге.

Поиск id по имени:

```
searchJiraIssuesUsingJql:
  jql: "project = PX AND sprint in openSprints() ORDER BY updated DESC"
  fields: ["customfield_10006"]
  maxResults: 5
```

В ответе `customfield_10006` — массив объектов со `id`, `name`, `state`,
`boardId`, `startDate`, `endDate`. Пример живого значения:
`{"id": 29280, "name": "PX Sprint 08.12 — 08.25", "state": "active", "boardId": 420}`.

Массив содержит и **закрытые** спринты тикета, поэтому ищи по `name`, а не по
позиции, и сверяй `boardId: 420`. Названного имени в выдаче нет — спроси id, а не
подставляй похожее: запрос находит только спринты, куда уже что-то положено, и
пустой спринт им не увидеть.

Ставь спринт при создании. Если Jira отклоняет поле на экране создания, проставь
его после через `editJiraIssue` тем же значением; при отказе на числе попробуй
массив (`[29280]`).

## Связь стори с задачей

Тип `Work item split` (id 10404). У него две подписи: `inward` = «split from»,
`outward` = «split to». Читается со стороны стори: Story split to Task.

```json
{
  "cloudId": "b7cc35a5-077d-4e65-890a-2134bf111631",
  "type": "Work item split",
  "inwardIssue": "PX-4797",
  "outwardIssue": "PX-5505"
}
```

`inwardIssue` — стори-источник, `outwardIssue` — новая задача; читается как
«Story split to Task». Проверено на существующей связи PX-5505 → PX-4797.
Обратный порядок создаёт связь, которая читается наоборот.

Остальные типы связей (`Blocks` — «is blocked by» / «blocks», `Relates`,
`Problem/Incident` — «is caused by» / «causes», `Duplicate`) ставятся только по
явной просьбе пользователя. Сам их не добавляй.

## Проверка результата

Ответ на создание содержит **не все** поля: у `editJiraIssue` схема прямо говорит,
что возвращается дефолтный набор чтения (summary, description, status, issuetype,
priority, labels, components, assignee, reporter, resolution, project), а `parent`,
оценка и спринт в него не входят. Состав ответа `createJiraIssue` схемой не
обещан вовсе.

Отсюда правило: то, что видно в ответе, сверяй по ответу. Про остальное не
утверждай, что оно проставилось. В отчёте пиши как есть — «передан `parent`
PX-3480, подтверждение не запрашивал», — и не выдумывай подтверждения, которого у
тебя нет.

Один читающий вызов `getJiraIssue` оправдан, только когда цена ошибки выше цены
шума: тикет уходит в спринт, который вот-вот берут в работу, или связь с эпиком
критична для отчётности. По умолчанию его не делай.

## Правка существующего тикета

`editJiraIssue` перезаписывает `description` целиком. Поэтому перед правкой чужого
текста **прочитай тикет** — `getJiraIssue` с `fields: ["summary","description"]` и
`responseContentFormat: "markdown"`, — покажи пользователю новую версию и дождись
«да». Без чтения ты не дописываешь, а стираешь.

Это единственное место в скилле, где читающий вызов обязателен: без него правка
разрушительна.

## Если запрос падает

**Cloudflare-страница «Attention Required!» вместо JSON.** WAF перед
MCP-эндпоинтом реагирует на код в теле запроса (curl, mongosh, JSON). Это
подтверждено на Confluence; на описании тикета с большим блоком кода возможно то
же.

Повтори вызов один раз: часть срабатываний разовые. Если повторилось — создай
тикет **без блока кода**, оставив на его месте строку «фрагмент кода — в
комментарии», и отдай блок пользователю, чтобы он вставил его руками. Не
экранируй код HTML-сущностями: при `contentFormat: "markdown"` они не
декодируются, и в тикете останется литеральный `&lt;`, то есть неверный код —
это хуже отсутствующего фрагмента.

**Поле отклонено.** Создай тикет без спорного поля и скажи пользователю, какое
поле Jira не приняла. Метаданные экрана создания не тяни (см. начало файла).

**MCP не подключён.** Порядок действий — в SKILL.md, шаг 5: отдать пользователю
готовый текст, ничего не имитируя.
