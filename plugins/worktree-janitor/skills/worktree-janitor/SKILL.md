# Чистка git worktrees

Worktrees копятся: задача уехала в мастер, PR влит сквошем, а каталог остался
на диске и занимает место. Опасность обратная — удалить дерево, в котором
лежит единственная копия работы. Задача скилла: по каждому worktree дать
доказуемый ответ «эту работу можно потерять» или «нельзя», и удалить только
те, по которым ответ доказан.

## Как работать

Работа идёт в два шага, и они разделены намеренно. Отчёт — всегда. Удаление —
только после того, как пользователь прочитал отчёт и назвал, что удалять.
Пользователь просил отчёт, а не уборку, пока он не сказал «удали».

Разрешение на удаление приходит одним из двух способов:

- флагом `--clean` в команде `/worktree-janitor:worktree-janitor` — пользователь
  разрешил уборку заранее, отдельного вопроса не нужно;
- словами в ответ на отчёт — «удали слитые», «снеси всё, что безопасно».

Без того и другого работа заканчивается на шаге 2. Шаги 3 и 4 — единая уборка:
получив разрешение, выполняй оба, иначе после удаления деревьев останутся
пустые каталоги, и пользователю придётся просить второй раз.

### Шаг 1. Собрать состояние

```bash
python3 <skill>/scripts/scan_worktrees.py [КАТАЛОГ]
```

Каталог берётся из аргументов команды или из просьбы пользователя. Если
каталог не назван, используй текущий. Скрипт обходит дерево, находит
репозитории, спрашивает у каждого его worktrees и печатает состояние. Он
ничего не меняет: не делает fetch, prune или remove.

Флаг `--json` даёт тот же результат машинно — бери его, если нужно посчитать
или отфильтровать worktrees программно, а не глазами.

Скрипт делает измерения, но не выводы. Выводы делаешь ты, и по спорным
случаям проверяй его вручную — как именно, написано ниже в разделе «Что легко
понять неправильно».

### Шаг 2. Написать отчёт

Веди отчёт от результата: сначала сколько нашлось и что из этого можно
удалять, потом подробности. Группируй по статусу, а не по репозиториям —
пользователь принимает решение по статусу.

Статусы, которые ставит скрипт:

| Статус | Значение | Удалять |
|---|---|---|
| `dirty` | есть незакоммиченные или неотслеживаемые файлы | нет |
| `local-only` | чисто, но коммитов нет ни на upstream, ни в дефолтной ветке | нет, это единственная копия |
| `pushed` | чисто, коммиты есть на upstream, но ещё не в дефолтной ветке | да, работа на remote |
| `merged` | чисто, вся работа уже в дефолтной ветке | да |
| `empty` | чисто, коммитов сверх дефолтной ветки нет | да |

Обязательно назови в отчёте возраст последнего `git fetch` по каждому
репозиторию. Все выводы про «запушено» и «слито» опираются на локальные копии
`origin/*`, а они устаревают. Если fetch старше суток, скажи это и предложи
обновить — но сам `git fetch` не запускай, пока пользователь не согласится.

Про коммиты внутри worktree отвечай по журналу ветки против дефолтной:
`git log --no-merges <default>..HEAD`. Скрипт уже собрал этот список в поле
`commits` при выводе `--json`.

### Шаг 3. Удалить — только по явной просьбе

Перед каждым удалением проверь, что пропадёт вместе с деревом:

```bash
git -C "$W" status --porcelain --ignored
```

Эта проверка — не формальность, а единственная защита игнорируемых файлов.
`git worktree remove` отказывается удалять дерево с изменёнными или
неотслеживаемыми файлами, но файлы из `.gitignore` стирает молча и без
предупреждения. А там лежат `.env`, локальные конфиги и ключи, которых нет
больше нигде.

Но не всякий игнорируемый файл стоит вопроса. Сканер делит их на два поля:

- `ignored_noise` — `.DS_Store`, каталоги IDE и сборки. Восстанавливаются сами,
  не хранят ничего. Упомяни числом в примечаниях и удаляй молча.
- `ignored_review` — всё остальное. Здесь останови удаление именно этого
  дерева, назови файлы и спроси.

Список мусора в сканере закрытый и узкий: незнакомое имя попадает в
`ignored_review`. Не расширяй его на ходу и не решай за пользователя, что файл
неважен — содержимое `.env` знает только он. Лишний вопрос стоит одной строки,
пропущенный — стёртого ключа.

Остановка с вопросом — это законченная работа, а не брошенная на середине.
Просьба «снеси ненужные» — это про деревья, судьба которых очевидна. Дерево с
чужим секретом внутри к ним не относится, и правильный результат по нему —
вопрос. Удали всё остальное, отчитайся по удалённому и задай вопрос по
оставшемуся: так пользователь получает и результат, и решение за собой.

```bash
git -C "$W" worktree remove "$W"
```

Без `--force`. Отказ команды — это защита, а не препятствие: она срабатывает
ровно тогда, когда в дереве осталось что-то несохранённое. Получив отказ,
разберись в причине и вернись к пользователю, а не обходи флагом.

Удаляй только worktrees. Ветки и коммиты оставляй на месте, даже если ветка
слита: восстановить worktree из ветки — одна команда, восстановить ветку из
удалённого worktree — уже нет. Если пользователь отдельно попросит удалить
ветки, это другая задача и другое подтверждение.

### Шаг 4. Убрать пустые каталоги

`git worktree remove` стирает само дерево, но каталог-родитель, заведённый под
репозиторий, остаётся пустым. Такие папки — след уборки, и оставлять их незачем.

```bash
python3 <skill>/scripts/prune_empty_dirs.py КОРЕНЬ          # показать
python3 <skill>/scripts/prune_empty_dirs.py КОРЕНЬ --apply  # удалить
```

Сначала без `--apply`: скрипт удаляет файлы, а не только каталоги, поэтому
сухой прогон обязателен. Покажи его вывод пользователю, если там есть хоть
что-то неожиданное.

Пустым скрипт считает и каталог, где остался только мусор из того же списка,
что и на шаге 3: папка с одним `.DS_Store` пуста по смыслу. Каталог с любым
другим файлом остаётся. Корень обхода не удаляется никогда — его заводил
пользователь.

Внутрь рабочих деревьев скрипт не заходит вообще. Это не перестраховка: снаружи
чекаут с одним `.DS_Store` выглядит пустым, а внутри у него служебные каталоги
`.git`, и обход по общему правилу снёс бы `refs/heads` вместе с ветками.

Под уборку попадут и пустые папки, не связанные с удалёнными деревьями. Назови
их отдельно — пользователь мог держать каталог под будущую работу.

После удаления покажи, что осталось: `git worktree list` по затронутым
репозиториям.

## Что легко понять неправильно

Здесь собраны ошибки, которые дают уверенный, но неверный ответ. Каждая
однажды привела к неправильному выводу «работа уникальна», после которого
worktree оставили висеть, либо к обратному — к предложению удалить нужное.

**`git cherry` слеп к squash-merge.** Он сравнивает коммиты по одному. Ветку
из девяти коммитов, влитую сквошем, он покажет девятью плюсами — как будто
работа нигде больше не существует. Скрипт закрывает эту дыру: он берёт
patch-id суммарного дифа ветки от точки ветвления и ищет его среди коммитов,
добавленных в дефолтную ветку после этой точки. Совпало — работа влита. Это
поле `squash_merged`.

**Большой диф против дефолтной ветки не значит, что ветка что-то содержит.**
`git diff origin/master HEAD` на 600 файлов почти всегда означает, что это
дефолтная ветка ушла вперёд, а не что worktree держит 600 файлов работы.
Чтобы увидеть работу самой ветки, сравнивай от точки ветвления:
`git diff $(git merge-base origin/master HEAD) HEAD --stat`.

**Проверяй вывод содержимым, а не только счётчиками.** Прежде чем назвать
работу слитой, подтверди это вторым способом: найди коммит в дефолтной ветке
(`git log origin/master --grep=<номер задачи>`) или убедись, что файлы ветки
совпадают с дефолтной (`git diff <default> HEAD -- <файлы ветки>` пуст).
Два независимых признака стоят одного счётчика.

**`git rev-parse --abbrev-ref --symbolic-full-name '@{u}'` врёт при отсутствии
upstream.** Он печатает саму строку `@{u}` и её легко принять за имя ветки.
Проверяй код возврата, а не вывод. Скрипт использует `HEAD@{upstream}` с
проверкой кода возврата.

**Stash общий на репозиторий, а не на worktree.** `git stash list` внутри
worktree покажет заначки всего репозитория. Не приписывай их конкретному
дереву и не считай признаком незавершённой работы именно в нём.

**Дефолтная ветка не всегда `master`.** Скрипт берёт её из
`refs/remotes/origin/HEAD` и откатывается к `origin/main`, `origin/master`.
Если ни одна не нашлась, сравнивать не с чем — так и скажи, не подставляй
`master` наугад.

**`ahead 0` против upstream не значит «слито».** Это значит «запушено».
Работа живёт на remote, worktree удалять можно, но ветка ещё ждёт ревью или
мержа. Это разные статусы, и пользователю важна разница.

## Формат отчёта

```markdown
## Результат
[Сколько репозиториев, сколько worktrees, сколько можно удалить.]

## Можно удалять (N)
[Таблица: worktree, ветка, почему безопасно — «слито в master (#25132)» или
«запушено на origin».]

## Нельзя удалять (N)
[По каждому: что именно держит, сколько коммитов или файлов, что с этим делать.]

## Примечания
[Возраст fetch, stash репозитория, locked и prunable записи, пустые каталоги.]
```

Таблицы — для сравнения коротких фактов. Разбор коммитов внутри ветки —
списком, а не таблицей.
