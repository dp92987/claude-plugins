# Тикет → PR

Скилл проводит тикет через конвейер: **вопросы → имплементация → pre-review →
коммит → пуш → PR → призыв ревьюеров**. Имплементация — единственный
обязательный шаг; остальные включаются профилем и выбором пользователя.
Порядок фиксирован: pre-review стоит до коммита, чтобы правки по нему легли в
тот же коммит и в историю ушёл результат, а не процесс.

Код пишет эта сессия. Внешние агенты участвуют только как ревьюеры на шаге
pre-review: их ценность — свежий контекст, а не авторство.

Всё командное — сайт Jira, именование ветки, команды проверки, модель
субагента pre-review, формат коммита, способ создать PR, способ призвать
каждого ревьюера — живёт в **профиле**: markdown-файле в каталоге данных
плагина. Здесь описан порядок; каждый шаг берёт значения из разделов профиля
по их именам.

## Два режима и один раунд вопросов

- **full** — выполняются все шаги, которые есть в профиле, без вопросов о
  процессе: пользователь заранее решил, что делать.
- **partial** — перед началом показывается чеклист шагов из профиля, и
  пользователь выбирает.

Вопросы о процессе — коммитить ли, кого звать — есть только в partial.
Вопросы о содержании — что именно строить — есть в обоих режимах, но задаются
один раз и до начала работы (шаг 2). Тикет с открытым решением, реализованный
по догадке, стоит дороже одной паузы: ревьюер получает уверенно сделанное не
то. После этого раунда вопросов нет — ни о процессе, ни о содержании, кроме
случая на шаге 4, когда работа вскрывает то, чего из тикета и кода было не
видно.

Команда указывает режим. Скилл, вызванный без команды, работает как partial.

## Шаги

### 0. Профиль

Каталог данных плагина — `${CLAUDE_PLUGIN_DATA}`. Если переменная не
подставлена, каталог ищется как
`~/.claude/plugins/data/ticket-to-pr-<marketplace>/`.

1. Прочитай `config.md`: маппинг «репозиторий → профиль».
2. Определи репозиторий: `git remote get-url origin`, нормализованный до
   `github.com/org/repo` (без схемы, `git@`, двоеточий и `.git`).
3. Выбери профиль по точному совпадению remote. Wildcard-строк и профиля по
   умолчанию нет намеренно: чужой профиль зовёт чужих ревьюеров.
4. Прочитай `profiles/<имя>.md` целиком. Разделы, на которые ссылаются шаги:
   «Jira», «Ветка», «Проверка», «Pre-review», «Коммит», «PR», «Ревьюеры».

**Профиль не нашёлся** (нет config.md или строки для remote) — проведи
настройку по `references/setup.md` прямо сейчас, в этой же сессии, и продолжи
с шага 1. Формат профиля — `references/profile-template.md`.

Необязательного раздела нет — шага нет: он не попадает в чеклист partial и не
выполняется в full. Заглушек и значений «по памяти» вместо раздела не бывает.

### 1. Тикет

Аргумент — ссылка `https://<site>.atlassian.net/browse/KEY-123` или голый
ключ `KEY-123`. Ключ из ссылки; сайт — из ссылки, а при голом ключе — из
раздела «Jira» профиля. Сайт ссылки не совпал с профилем — остановись и скажи:
тикет чужой Jira не читается через `cloudId` этого профиля.

Прочитай тикет через Atlassian MCP (`getJiraIssue`, `cloudId` из профиля;
загрузи инструмент одним ToolSearch). Нужны: заголовок, описание целиком,
критерии приёмки / DOD, родитель или связанная стори, комментарии — в них часто
лежит уточнение постановки. Тикет — источник «что»; «как» ты решаешь по коду.

Тикет не читается (нет доступа, нет ключа, MCP недоступен) — остановись.
Имплементировать по названию ветки или по памяти нельзя.

### 2. Открытые вопросы и чеклист — один раунд

Прочитай код до **локализации**: назови сервис, файлы и функции, которых
работа касается, и как задача ложится на существующие паттерны. Только после
этого видно, что тикет оставил открытым: интервал по умолчанию, имя поля,
поведение на границе, «чиним отображение или причину», раздел `## Открытый
вопрос` в самом тикете. Собери всё в список; каждый вопрос — с вариантами,
которые ты видишь в коде, и тем, что выбрал бы сам и почему. Вопрос без
вариантов возвращает работу пользователю целиком; вопрос с вариантами — только
решение.

Затем один `AskUserQuestion`:

- **partial** — чеклист шагов плюс открытые вопросы;
- **full** — только открытые вопросы; нет вопросов — нет и раунда.

Инструмент берёт до четырёх вопросов за вызов. Не влезло — второй вызов сразу
за первым, до начала работы; «один раунд» значит «до того, как тронут код», а
не «один вызов». Больше шести открытых вопросов — признак, что тикет не готов:
скажи это и спроси, продолжать ли.

Чеклист собирается из профиля:

| Шаг | Есть, если в профиле |
| --- | --- |
| pre-review субагентом | «Pre-review» перечисляет субагента |
| pre-review Codex | «Pre-review» перечисляет codex |
| коммит | «Коммит» |
| пуш | «Коммит» (пуш без формата коммита не бывает) |
| создать PR | «PR» |
| призвать `<ревьюер>` — по строке на каждого | «Ревьюеры» |

Каждый шаг — опция `multiSelect` с коротким описанием того, что он сделает
(«коммит одним сообщением по формату профиля», «комментарий `@claude` в PR»).
Имплементация в чеклисте не показывается — она базовая. В full включены все
доступные шаги.

Зависимости: пуш требует коммита, PR — пуша, призыв — PR. Выбрано следствие
без причины — включи причину и назови это в первой же строке ответа, а не
спрашивай второй раз: пользователь выбрал результат, а не ритуал.

Ответы на открытые вопросы — часть постановки: они идут в контекст pre-review
и в тело PR, чтобы ревьюер видел решение, а не искал его в диффе.

### 3. Ветка

Раздел «Ветка» профиля задаёт базовую ветку и шаблон имени.

- Текущая ветка — базовая: создай ветку по шаблону от свежей базы
  (`git fetch origin <база>`, `git switch -c <имя> origin/<база>`). Дерево при
  этом должно быть чистым: чужие незакоммиченные правки в ветке тикета — не
  твои изменения, и ревьюер их не поймёт. Грязное — остановись и скажи.
- Текущая ветка не базовая и содержит ключ тикета — работай в ней: пользователь
  уже начал.
- Текущая ветка не базовая и ключа не содержит — остановись и спроси: коммит
  в чужую ветку — то, что нельзя откатить одной командой.

Worktree скилл не создаёт: где работать, пользователь решает до вызова
штатными средствами Claude Code.

### 4. Имплементация

Работай как над обычной задачей из тикета, с решениями из шага 2.

**Вопрос, который вскрылся только в работе** — то, чего не было видно ни из
тикета, ни при локализации, и что меняет наблюдаемое поведение, — задаётся
сразу, в обоих режимах: «без вопросов» в full относится к процессу, а не к
тому, что строим. Решения, поведения не меняющие (имя приватной функции,
структура теста), принимаешь сам и перечисляешь в отчёте.

**Проверка — из профиля.** Раздел «Проверка» перечисляет команды (тесты, линт,
генерация). Прогони их после имплементации; красный результат чинится до
pre-review, не откладывается на ревьюера. Раздела нет — прогони то, что
очевидно из репозитория (`go test ./...` рядом с изменёнными пакетами), и в
отчёте назови, что запускал.

Регрессионный тест кладётся туда, где баг проявился, — в обработчик или точку
интеграции, а не только у изменённого примитива.

### 5. Pre-review

Выбранные ревьюеры запускаются параллельно на одном и том же диффе — все
изменения ветки против базы плюс незакоммиченное. Как именно: субагент с
моделью из профиля, `codex exec review` с контекстом тикета и решений шага 2,
проверка находок, исправление и одна повторная проверка — в
`references/pre-review.md`. Прочитай его перед первым запуском ревью.

Итог шага — три списка: исправлено, отклонено (с причиной), осталось. Оставшееся
идёт в тело PR секцией «Замечания pre-review» и в отчёт. Пустое ревью — тоже
результат: назови, кто смотрел и что.

Ревьюер недоступен (нет `codex`, не залогинен, модель не поднялась) — не
подменяй его молча собой: пропусти, продолжи конвейер и назови пропуск в
отчёте. Самопроверка автора — не независимое ревью, которое обещал профиль.

### 6. Коммит

Формат сообщения — раздел «Коммит» профиля. Стейджь изменённые тобой пути
явно (`git add <файлы>`), не `git add -A`: рядом могут лежать чужие файлы.
Один коммит на тикет, если работа не распадается на независимые куски сама;
правки по pre-review в отдельный коммит не выделяются — они часть той же
работы.

Трейлеры авторства ставятся так, как велит окружение сессии.

### 7. Пуш

`git push -u origin <ветка>`. Никогда `--force`: ветка могла быть начата
пользователем и запушена раньше. Отклонённый пуш — остановись и покажи вывод.

### 8. PR

Раздел «PR» профиля называет способ, и только он: другие скиллы на этом шаге
не консультируются, если профиль их не назвал, — иначе тело PR напишется по
чужим правилам, а профиль команды окажется декорацией.

- **Скилл** — профиль называет скилл-создатель PR по имени: вызови его через
  Skill и передай в контексте всё, что он иначе спросил бы — ссылку на тикет,
  что сделано, решения открытых вопросов, что запускал на проверке и с каким
  результатом, оставшиеся замечания pre-review. Заголовок и тело — его правила;
  секции «Решения» и «Замечания pre-review» попроси добавить в тело, если
  непустые.
- **`gh pr create`** — заголовок и тело по правилам, записанным в разделе «PR»
  профиля; те же две секции в теле.

Хуки других плагинов могут заблокировать создание PR. Их сообщение говорит,
что сделать; выполни и повтори. Это ожидаемая часть процесса, не сбой.

### 9. Призвать ревьюеров

Раздел «Ревьюеры» профиля — таблица «имя → команда» с `<pr>` вместо номера.
Выполни команду каждого выбранного ревьюера с номером созданного PR. Команда
упала — покажи вывод и продолжи с остальными.

### 10. Отчёт

Одно сообщение, по которому понятно, что произошло, без чтения транскрипта:

- ветка и коммит (или «не закоммичено»);
- ссылка на PR (или «PR не создавался»);
- кто призван;
- pre-review: кто смотрел, сколько исправлено / отклонено / осталось;
- решения открытых вопросов и мелкие решения, принятые в работе;
- что пропущено и почему (ревьюер недоступен, шаг не выбран).

Ключи, ссылки и номера — из вывода команд этой сессии, не по памяти.
