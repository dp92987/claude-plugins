# Деплой ветки тикета

Как `/ticket-to-pr:deploy` выкатывает ветку: чеклист, как проверяется каждый
пункт, health check и формат отчёта. Все адреса, джобы, контексты и сроки —
из раздела «Деплой» профиля; здесь только порядок и правила.

Принцип один: **команда проверяет и докладывает, но не чинит.** Любой ❌ —
останов на этом пункте, оставшиеся пункты получают ⏭, и пишется отчёт. Не
откатывай, не перезапускай поды, не занимай сервис в боте блокировок, не
снимай чужую блокировку, не мержи master руками при конфликте: каждое из этих
действий меняет чужое окружение, и решение о нём принимает человек.

## Как читать CI-систему

Логи сборок и деплоев читай **по шагам**, а не целиком: полная консоль
большой сборки отдаётся минутами и обрывается на середине, и нужная строка
просто не доходит. Как получить список шагов и лог одного шага — в профиле
(у Jenkins — `wfapi`). Список запусков джобы запрашивай в два приёма: сначала
номера и признак «идёт», потом параметры только нужных запусков — запрос с
параметрами по всем запускам сразу тоже обрывается. Полную консоль не читай
даже ради последней строки: `tail` ждёт весь ответ, и команда виснет так же.
Итог запуска — из API стадий (у Jenkins `wfapi/describe`, поле `status`).

Ответ, оборванный посередине (невалидный JSON, нет итоговой строки), — не
«строки нет», а «не прочитано»: повтори узким запросом; не вышло — ❌ «не
удалось прочитать», а не вывод по обрывку.

## Контуры и запуски

Контуры — ровно те, что названы в аргументах. Контур, которого нет в таблице
контуров профиля, — ❌ с перечнем известных.

На dev результат — сам выкат; health check гоняется только на прод-контурах.

- **Только dev** — один запуск, без health check: итог — результат выката
  (пункт 12); пункты 13–15 — «dev не проверяется».
- **Только прод** — один запуск, health check каждого прод-контура целиком
  (пункты 13–15).
- **dev и прод** — **один** запуск джобы на все контуры, health check только
  прод-контуров.

## Что писать по ходу

Команда идёт десятки минут, и пользователь должен видеть, на каком она шаге.
На каждом переходе — одна короткая строка в чат, без подробностей; подробности
только в итоговом отчёте:

- `Выполняю подготовку…` → `Подготовка ✅` (пункты 1–10; ожидание CI или
  сборки называется отдельной строкой: `Жду CI…`, `Жду сборку №N…`);
- `Деплою на dev…` → `dev ✅` — по стадии контура в запуске, когда она
  закончилась;
- `Деплою на <прод-контур>…` → `<прод-контур> ✅`;
- `Смотрю health check…` → `Health check ✅` (после второго чека и вердикта
  referee).

На ❌ строки дальше не пишутся — сразу отчёт.

## Чеклист

Пункты идут в этом порядке; номер пункта — его строка в отчёте.

### Вход

1. **Тикет, ветка, PR.** Ключ тикета — из аргумента или имени ветки. Ветка —
   ветка тикета (ворктри, где она выкачана, как в шаге 4 конвейера), PR —
   открытый PR этой ветки (`gh pr view <ветка> --json number,url,body`). Нет PR
   — ❌: секции «Деплой» взять неоткуда.
2. **Сервисы и порядок.** Из секции «Деплой» тела PR: блок «Деплой» —
   сервисы в порядке выкатки. «Не требуется» — ❌ с цитатой: катить нечего.
   Для каждого сервиса — путь приложения по шаблону профиля
   (`<domain>/cmd/<svc>/deploy`) и проверка, что каталог существует.
   Контуры блока «Деплой» и аргументы разошлись — не ❌: катятся контуры из
   аргументов, а расхождение называется в строке пункта («в PR только
   mp.us-east-2, dev — по аргументу»), чтобы оно было видно в отчёте.
3. **Контуры разрешены.** Для каждого сервиса и контура: у манифеста
   `Deployment` в каталоге приложения (база плюс подкаталог контура, если
   есть) аннотация `allowed-datacenters` содержит контур. Иначе ❌: джоба
   молча пропустит манифест и закончится зелёной без выката.
4. **«До деплоя» выполнено.** Блок «До деплоя» тела PR. «Нет.» — ✅. Иначе
   каждый пункт: проверяемое — проверь (ключ конфига — чтением конфига
   способом из профиля), непроверяемое (значение секрета, ручное действие в
   другой системе) — спроси пользователя одним списком. Не подтверждено — ❌.

### Код и сборка

5. **Master актуален.** `git fetch origin <база>`. База ушла вперёд ветки —
   смотри, что в ней изменилось: `git diff --name-only HEAD...origin/<база>`.
   Мержить нужно, только если изменения задевают выкатываемые сервисы: файлы
   в каталоге сервиса, в каталогах пакетов, которые он импортирует (`go list
   -deps ./<каталог сервиса>/...` внутри модуля), `go.mod`/`go.sum`. Тогда
   `git merge --no-edit origin/<база>` и `git push` (без `--force`): новый
   коммит значит новый CI и новую сборку. Не задевают — не мержи: прогон CI и
   сборки ради чужих правок стоит полчаса и ничего не меняет в образе; в
   отчёте пункт — ✅ с числом коммитов базы впереди и пометкой, что сервисы
   они не задевают. Конфликт — `git merge --abort` и ❌ со списком файлов.
   Затем HEAD ветки равен `origin/<ветка>`.
6. **CI на HEAD зелёный.** Те же условия, что в D2, без требований к ревью:
   каждая проверка `statusCheckRollup` завершилась, `CheckRun` — `SUCCESS`,
   `SKIPPED` или `NEUTRAL`, `StatusContext` — `SUCCESS`. Проверки сторонних
   систем (Jenkins: интеграционные тесты, coverage) входят в список наравне с
   Actions. Идут — жди через `Monitor` до срока «CI» из профиля; упала или
   срок вышел — ❌ с именем проверки и ссылкой.
7. **Сборка из HEAD.** Номер сборки — из ссылки статуса сборки ветки в
   `statusCheckRollup` (имя статуса — в профиле). Сборка должна:
   - быть собрана из HEAD: коммит из артефакта сборки или строки
     `Checking out Revision <sha>` её консоли равен HEAD;
   - закончиться `SUCCESS`;
   - содержать каждый сервис из пункта 2 в списке собранных или перетеганных
     приложений (строки консоли — в профиле).
   Идёт — жди до срока «Сборка». Сервиса в сборке нет — ❌: катить нечего,
   образ остался бы прежним.

### Окружение

8. **Прямо сейчас никто не катит.** Среди идущих запусков джобы деплоя
   (`building: true`) нет запуска, чьи `Applications` содержат путь
   приложения из пункта 2. Есть — ❌ с номером запуска и тем, кто запустил.
9. **Блокировки.** Прочитай сообщения бота блокировок из профиля для каждого
   контура. Сообщение старше 5 минут по своей метке времени — ❌: бот мог
   встать, и пустой список ничего не доказывает. Для каждого сервиса нужны
   оба условия: блокировки чужих людей нет, блокировка пользователя есть.
   Пользователь — текущий пользователь Slack MCP (`slack_read_user_profile`
   без аргументов). Нет своей — ❌ «займи сервис в боте»: сам не занимай.
   Своя есть, но остаток меньше p90 срока «Деплой» из профиля плюс 10 минут
   на health check (без прод-контуров — без этих 10 минут) — ❌ «продли
   блокировку в боте»: блокировка истекла бы посреди выката, а
   предупреждение в отчёте прочитают уже после него.
10. **Что стоит сейчас.** Для каждого сервиса и контура:
    `kubectl --context <контекст> -n <namespace> get deploy <svc> -o
    jsonpath='{.metadata.labels.buildNumber} {.spec.template.spec.containers[0].image}'`.
    Тег образа — `<ветка>-<номер сборки>`. Из него — цель отката:
    - ветка `master` или ветка, которая ещё есть в `origin`
      (`git ls-remote --heads origin <ветка>`), — эта пара ветка + номер;
    - ветки в `origin` больше нет (PR смержен, ветка удалена) — последняя
      успешная сборка базовой ветки (как её найти — в профиле): джоба деплоя
      выкачивает ветку из параметра, и по удалённой ветке запуск падает на
      checkout, даже если образ в реестре цел.
    Контекст недоступен — ❌: без него не будет и health check.

### Деплой

11. **Запуск.** `buildWithParameters` джобы деплоя с параметрами из профиля:
    ветка, номер сборки из пункта 7, `Applications` — пути из пункта 2 через
    запятую в порядке PR, `Datacenters` — контуры через запятую, проверка
    master включена. По `Location` ответа дождись номера запуска в очереди и
    сверь, что параметры запуска совпали с отправленными.
12. **Выкат.** Жди окончания до срока «Деплой» через `Monitor`, который
    будит только по делу: завершилась стадия контура, кроме последнего
    (строка «<контур> ✅»), упала любая стадия, закончился запуск — последний
    контур идёт в этом же событии. Служебные стадии (checkout, проверка
    master) не будят: каждое событие — полный ход модели с чтением всего
    контекста, а пользы от них нет. Скрипт монитора — в профиле. Итог
    запуска — `SUCCESS` по API стадий, не по полной консоли.
    Затем в логах шагов стадии каждого контура: стадия контура есть, образ
    подменён на тег из пункта 7, по каждому сервису `successfully rolled
    out`. Строка о пропуске
    `Deployment` нужного сервиса из-за `allowed-datacenters` — ❌, даже при
    зелёном итоге.

### Health check

13. **Сразу после выката** — по каждому прод-контуру запуска (см. «Контуры и
    запуски»), таблица ниже. Только dev — пункты 13–15 «dev не проверяется».
14. **Через 5 минут** — те же проверки ещё раз (Bash в фоне `sleep 300`, не
    передний план).
15. **Вердикт deploy-referee** — по каждому прод-контуру запуска, где консоль
    деплоя показывает вызов судьи, а не строку `deploy-referee: skipping judge
    call`. Вердикт приходит сообщением в канал из профиля после окна сервиса
    (обычно 5 минут после выката): ищи сообщение с `Service: <project>/<svc>`,
    `Datacenter: <контур>` и `Run: -<номер запуска деплоя>`. Жди до 10 минут
    после выката, через `Monitor`. `PASS` — ✅; `FAIL` и `UNCERTAINTY` — ❌ с
    сигналами из сообщения; не пришло в срок — ❌ «вердикта нет». Судья не
    вызывался — строка «не вызывался» без ❌.

После всех трёх — если прод-контур в запуске и всё ✅, доведи тикет до
статуса `После деплоя:` из «Статусов» по правилам шага 3. Dev-только деплой
тикет не двигает.

## Health check: что проверяется

Для каждого сервиса в контуре; namespace и `app`-лейбл — из манифеста.

| Проверка | Как | ❌ когда |
| --- | --- | --- |
| rollout | `kubectl rollout status deploy/<svc> --timeout=60s` | не завершился |
| Ready | поды по `-l app=<svc>`: Ready / `spec.replicas` | не все Ready |
| образ | `image` каждого пода | хоть один не с тегом из пункта 7 |
| рестарты | `restartCount`, `state.waiting.reason`, `lastState.terminated.reason` | рестарт > 0, `CrashLoopBackOff`, `OOMKilled` |
| старый ReplicaSet | `kubectl get rs -l app=<svc>` | у не текущего RS `replicas` > 0 |
| ошибки в логах | OpenSearch контура: число записей `level: error` сервиса за 5 минут до выката и за окно после старта (см. ниже) | после > 2× до и > 10 |
| воркер: lag | VictoriaMetrics: `kafka_consumergroup_lag` группы сервиса в контуре | на втором чеке больше, чем на первом, и > 100 |
| HTTP: 5xx | VictoriaMetrics: доля 5xx в запросах сервиса за 5 минут | > 1% и выше, чем до выката |

Окно ошибок после выката начинается через минуту после старта последнего
нового пода (`containerStatuses[].state.running.startedAt`): при старте
сервис пишет ошибки, которые к ветке отношения не имеют (разбор конфигов с
неизвестными полями и т.п.), и они дали бы ложный ❌. Ошибки до начала окна
не считаются, а в отчёте перечисляются отдельной строкой «при старте: N»
с текстом самой частой. На первом чеке окно может быть ещё пустым — тогда
строка «окно после старта не набралось», решение по второму чеку.

CPU, память, троттлинг и p99 латентности сами не считаются: их оценивает
deploy-referee (пункт 15) по своим порогам, общим и на сервис в ConfigApp.

Сервис воркер, если его consumer group есть в метриках контура; HTTP — если
у него есть метрика запросов. Ни того, ни другого — строка «нет метрик» без
❌. Пороги — по умолчанию; профиль может задать свои.

## Отчёт

Одно сообщение. Заголовок — тикет, сервисы, контуры и итог (✅ / ❌ на каком
пункте). Дальше пункты чеклиста одной строкой каждый: ✅, ❌ с причиной или ⏭
не выполнялся. Ссылки — на сборку, на запуск деплоя, на упавшую проверку.

- **Успех** — после пунктов таблица health check по контурам и чекам, статус
  тикета и строка отката.
- **Провал** — пункты до провала, ❌ с фактами (имя пода, причина, строка
  лога), «что не делал» и строка отката, если выкат уже был.

Строка отката — параметры запуска джобы деплоя с целью отката из пункта 10,
по каждому контуру, и всегда с выключенной проверкой master: откат намеренно
катит сборку старее головы ветки, и проверка его бы отклонила.

Отчёт — **ровно по шаблону ниже**, без своих разделов:

- одна строка на пункт: номер, значок, короткий факт. Значки только ✅, ❌,
  ⏭; пункт, который по правилам не делается (health check dev, судья не
  вызывался), — ✅ или ⏭ с короткой причиной, а не «—»;
- пункты 13–15 списком не расписываются: при health check это таблица после
  пунктов, вердикт referee — её строкой; без health check — одна строка
  «13–15. ⏭ dev не проверяется»;
- пояснения, ход обсуждения, решения пользователя по ходу — не в строке
  пункта: решение сокращается до факта («база впереди на 1 коммит, сервисы
  не задевает»);
- наблюдения о самом скилле, профиле или окружении (что поправить, что
  тормозило) — **отдельным сообщением после отчёта**, не внутри него.

```markdown
7. ✅ Сборка back-delta/PX-6124-…/3 из 8ac0d71a48, образ :PX-6124-keep-leg-mismatch-filter-pushes-3
8. ✅ Идущих деплоев сервиса нет
9. ✅ Блокировка dev: твоя, чужих нет

```
