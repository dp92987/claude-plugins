# Pre-review

Ревью до коммита, чужими глазами. Автор слеп к собственным допущениям, поэтому
ревьюер получает свежий контекст: не эту сессию, а тикет, дифф и репозиторий.
Ревьюеры — модели, которые перечисляет раздел «Pre-review» профиля; выбранные
запускаются параллельно на одном диффе.

## Что смотрим

Дифф ветки против базы плюс незакоммиченное:

```bash
BASE="$(git merge-base HEAD origin/<база>)"
git diff "$BASE"                      # закоммиченное + staged + unstaged
git ls-files --others --exclude-standard   # новые файлы — diff их не покажет
```

Все ревьюеры получают один и тот же контекст тикета: ключ, заголовок, суть
постановки в одном абзаце и решения открытых вопросов из шага 2. Без него
ревьюер спорит с постановкой («зачем вообще X?») вместо того, чтобы проверять
реализацию.

## Как запустить ревьюера

Профиль называет модель и усилие, а не способ запуска: способы приходят и
уходят вместе с инструментами, а требование к ревьюеру одно. Механизм выбирает
окружение сессии — первое, что в нём есть:

1. **Модель провайдера этой сессии** — встроенный инструмент субагентов
   (в Claude Code — `Agent` с `model` и `effort`,
   `subagent_type: general-purpose`).
2. **Инструмент окружения, который запускает агента на модели другого
   провайдера** — оркестратор, делегирование задач. Следуй его собственным
   правилам: что вызвать перед первым запуском, как передать модель и
   настройки, как дождаться результата.
3. **CLI провайдера модели** в `PATH` (у моделей OpenAI — `codex`).

Ничего нет — ревьюер пропускается, пропуск идёт в отчёт. Не подменяй его
другой моделью и тем более собой: независимый взгляд — вся ценность шага.

Механизм годится, только если даёт всё это; не даёт — бери следующий:

- **модель и усилие из профиля** — тем параметром, который у механизма есть.
  Не указанное в профиле не передаётся, остаётся умолчание механизма. Усилие
  задать нечем — запусти без него и назови это в отчёте;
- **свежий контекст** — ревьюер не видит эту сессию;
- **то же дерево** — ревьюер видит незакоммиченное в ворктри тикета, поэтому
  без изолированной копии и отдельного чекаута. Механизм работает только в
  своей копии — запиши дифф и новые файлы в файл и передай его вместе с путём
  к репозиторию;
- **полный итог** — ответ ревьюера целиком, сообщением или файлом. Обрывок
  лога или частичный вывод — не итог: перезапусти;
- **ожидание по сигналу механизма** — уведомление о завершении или ответ
  вызова, а не цикл по списку процессов.

**Семейство и версия.** Профиль называет семейство (`opus`, `sol`) или точный
id. Семейство превращается в самую свежую модель семейства тем, что знает
механизм: встроенный `Agent` Claude Code сам понимает псевдоним (`opus`),
оркестратор отдаёт список моделей, CLI — каталог (у Codex —
`codex debug models`, свежайший `*-sol` с `visibility: list`). Точный id
передаётся как есть; механизм его не принимает (тот же `Agent` берёт только
псевдоним) — передай псевдоним его семейства, это не повод брать следующий
механизм. Какая версия ответила, видно по первой строке ответа ревьюера
(промпт просит назвать свой id): она идёт в отчёт, а расхождение с
закреплённым id — событием журнала.

Промпт — общий для всех ревьюеров, с подставленными значениями. Механизму,
который берёт промпт файлом, пиши его через Write, а не heredoc: в
ворктри-изоляции харнесс отказывает команде с heredoc и редиректами («too
complex to verify», PX-5985, PX-5984, 2026-10-19).

```text
Ты независимый ревьюер. Проверь изменения в репозитории <путь к корню> против
origin/<база>: коммиты с merge base, staged, unstaged и новые файлы
(`git diff <BASE>` плюс `git ls-files --others --exclude-standard`).
Проверяй adversarially: ищи самые сильные причины, почему это не должно уехать
в PR, не подтверждай.

Тикет <KEY-123>: <заголовок>. <Абзац постановки.>
Решения открытых вопросов, принятые с автором тикета: <список или «нет»>.

Читай не только дифф — открывай вызывающий код и тесты, чтобы понять, что
изменение ломает вокруг себя.

Приоритет — дорогие и незаметные отказы: границы доверия, потеря или порча
данных, гонки и порядок операций, пустые/nil/timeout-пути, откат и частичный
сбой, совместимость с уже задеплоенным. Стиль и вкус не трогай.

Первой строкой ответа назови свой точный id модели. Дальше — список находок:
серьёзность, file:line, конкретный сценарий отказа,
направление фикса. Только то, что можешь защитить кодом; одна сильная
находка лучше трёх слабых. Нет существенных находок — скажи прямо и назови
пробелы в тестах.
```

## Что уже известно о механизмах

Записано с живых прогонов. Это не указание выбирать именно их, а то, на чём
они уже ломались.

### CLI Codex

- Доступность — один раз за сессию: `codex --version && codex login status`.
- Запуск — из cwd ворктри, без `cd` (у `codex exec review` нет флага `-C`);
  промпт — в stdin из файла, итог — в файл `-o`, лог целиком, без `tail`:
  `session id` печатается в начале и нужен для уточнений.

  ```bash
  codex exec review -m <модель> -c model_reasoning_effort="<усилие>" -o <scratchpad>/codex-review.md - < <scratchpad>/codex-prompt.md > <scratchpad>/codex-review-run.log 2>&1
  ```

  Что не указано в профиле, флагом не передаётся и берётся из
  `~/.codex/config.toml` пользователя.
- Флаги цели (`--uncommitted`, `--base`) с кастомным промптом CLI не
  принимает — цель названа первой строкой промпта.
- Фоном запускается сама команда `codex`, без `&`, `nohup` и обёрток: харнесс
  уведомляет о завершении той команды, которую запустил, а обёртка с
  `codex … &` выходит сразу, и Codex остаётся сиротой. Ждать через
  `pgrep -f '<часть команды>'` нельзя: шаблон находит и сам цикл ожидания, и
  цикл не завершается никогда.
- Фоновый Codex умирает вместе с сессией Claude Code. После рестарта сессии
  посреди pre-review проверь, есть ли файл `-o`: нет — запуск оборвался,
  перезапусти ту же команду, а не читай обрывок лога как итог (PX-6212,
  2026-10-20).
- `<scratchpad>` — каталог scratchpad сессии, если окружение его даёт, иначе
  `mktemp -d`.

## Проверка находок

Каждую находку сверь с кодом до того, как что-то чинить. Ревьюер не знает
сессии: часть находок — сознательные решения или неверно прочитанное
намерение. Три исхода на находку:

- **подтверждена** — воспроизводимый сценарий отказа есть в коде → чинится;
- **отклонена** — с причиной в одну строку (решение тикета, ревьюер не увидел
  вызывающий код, поведение намеренное) → в отчёт как отклонённая;
- **не проверена** — не хватило времени или доступа → не чинится и не
  выдаётся за подтверждённую; идёт в «осталось».

Совпадение двух ревьюеров — сильный сигнал, но не доказательство: сверяй так
же.

## Исправление и повторная проверка

Подтверждённые находки исправь, повтори шаг 5а (SKILL.md) — и шаг 5б,
если исправление задело код, которым доказан критерий, — затем запусти тех
же ревьюеров ещё один раз на новом диффе. Один
раз — не до зелёного: второй круг проверяет, что фиксы не сломали соседнее и
не породили новых находок того же класса; третий и дальше — уже спор о вкусе,
который принадлежит живому ревью в PR. Что осталось после второго круга,
уходит в отчёт с исходом каждой находки; в тело PR — нет.

Уточнить у ревьюера его же находку («правда ли 2 эксплуатируема?») — в той же
его сессии, если механизм это даёт: продолжением субагента или делегированной
задачи, у CLI Codex — `codex exec resume <session-id> -o <out> "вопрос"` с id
из лога. Не даёт — новый запуск с находкой в промпте.
