# Pre-review

Ревью до коммита, чужими глазами. Автор слеп к собственным допущениям, поэтому
ревьюер получает свежий контекст: не эту сессию, а тикет, дифф и репозиторий.
Ревьюеров два вида, оба перечисляет раздел «Pre-review» профиля; выбранные
запускаются параллельно на одном диффе.

## Что смотрим

Дифф ветки против базы плюс незакоммиченное:

```bash
BASE="$(git merge-base HEAD origin/<база>)"
git diff "$BASE"                      # закоммиченное + staged + unstaged
git ls-files --others --exclude-standard   # новые файлы — diff их не покажет
```

Оба ревьюера получают один и тот же контекст тикета: ключ, заголовок, суть
постановки в одном абзаце и решения открытых вопросов из шага 2. Без него
ревьюер спорит с постановкой («зачем вообще X?») вместо того, чтобы проверять
реализацию.

## Субагент

`Agent` с `model` из профиля, `subagent_type: general-purpose`. Без
`isolation: worktree`: ревьюер должен видеть незакоммиченный дифф в этом же
дереве. Промпт — по этому образцу, с подставленными значениями:

```text
Ты независимый ревьюер. Проверь изменения в репозитории <путь к корню>
adversarially: ищи самые сильные причины, почему это не должно уехать в PR,
не подтверждай.

Тикет <KEY-123>: <заголовок>. <Абзац постановки.>
Решения открытых вопросов, принятые с автором тикета: <список или «нет»>.

Дифф: `git diff <BASE>` плюс новые файлы из `git ls-files --others
--exclude-standard`. Читай не только дифф — открывай вызывающий код и тесты,
чтобы понять, что изменение ломает вокруг себя.

Приоритет — дорогие и незаметные отказы: границы доверия, потеря или порча
данных, гонки и порядок операций, пустые/nil/timeout-пути, откат и частичный
сбой, совместимость с уже задеплоенным. Стиль и вкус не трогай.

Ответ — список находок: серьёзность, file:line, конкретный сценарий отказа,
направление фикса. Только то, что можешь защитить кодом; одна сильная
находка лучше трёх слабых. Нет существенных находок — скажи прямо и назови
пробелы в тестах.
```

## Codex

Проверь доступность один раз за сессию:

```bash
codex --version && codex login status
```

Не прошло — ревьюер пропускается, пропуск идёт в отчёт. Не подменяй Codex
собой: свежий контекст — вся ценность шага.

Запуск в фоне, итог — в файл; лог целиком, без `tail`: `session id` печатается
в начале и нужен для уточняющих вопросов Codex.

```bash
codex exec review -o <scratchpad>/codex-review.md - > <scratchpad>/codex-review-run.log 2>&1 <<'EOF'
Review the uncommitted and branch changes against origin/<база> (staged,
unstaged, untracked, and commits since the merge base).
Context: ticket <KEY-123> — <заголовок>. <Абзац постановки.>
Decisions agreed with the ticket author: <список или none>.
Review adversarially: find the strongest reasons this should not ship yet; do
not validate it. Prioritize expensive, hard-to-detect failures: trust
boundaries, data loss or corruption, races and ordering, empty/nil/timeout
paths, rollback and partial failure, compatibility with what is deployed.
For each finding give severity, file:line, the concrete failure mode, and a
fix direction. Only findings you can defend from the code; no style notes.
If the change looks safe, say so and name residual test gaps.
EOF
```

Флаги цели (`--uncommitted`, `--base`) с кастомной инструкцией CLI не
принимает — цель названа первой строкой промпта. Модель не переопределяй:
`~/.codex/config.toml` пользователя уже задаёт её.

`<scratchpad>` — каталог scratchpad сессии, если окружение его даёт, иначе
`mktemp -d`.

## Проверка находок

Каждую находку сверь с кодом до того, как что-то чинить. Ревьюер не знает
сессии: часть находок — сознательные решения или неверно прочитанное
намерение. Три исхода на находку:

- **подтверждена** — воспроизводимый сценарий отказа есть в коде → чинится;
- **отклонена** — с причиной в одну строку (решение тикета, ревьюер не увидел
  вызывающий код, поведение намеренное) → в отчёт как отклонённая;
- **не проверена** — не хватило времени или доступа → не чинится и не
  выдаётся за подтверждённую; идёт в «осталось».

Совпадение двух ревьюеров — сильный сигнал, но не доказательство: сверяй так
же.

## Исправление и повторная проверка

Подтверждённые находки исправь, прогони команды из раздела «Проверка»
профиля, затем запусти тех же ревьюеров ещё один раз на новом диффе. Один
раз — не до зелёного: второй круг проверяет, что фиксы не сломали соседнее и
не породили новых находок того же класса; третий и дальше — уже спор о вкусе,
который принадлежит живому ревью в PR. Что осталось после второго круга,
уходит в тело PR секцией «Замечания pre-review» и в отчёт, с исходом каждой
находки.

Уточнить у Codex его же находку («правда ли 2 эксплуатируема?») — через ту же
сессию, id из лога:

```bash
codex exec resume <session-id> -o <out> "вопрос"
```
