# Формат профиля

Профиль — markdown-файл `profiles/<имя>.md` в каталоге данных плагина
(`${CLAUDE_PLUGIN_DATA}`). Один профиль = один способ вести тикет до PR для
одной команды; репозиториев к нему может быть привязано несколько. SKILL.md
ссылается на разделы по именам, поэтому имена разделов — контракт: не
переименовывай их.

Правило чтения: **нет раздела — нет шага.** Шаг не показывается в чеклисте
partial и не выполняется в full. Поэтому необязательные разделы не заполняются
заглушками: пустой раздел «Ревьюеры» означает «звать некого», а выдуманная
команда призыва упадёт на живом PR.

У факта, снятого с репозитория или сервиса (cloudId, логин бота, шаблон ветки,
подсмотренный в `git branch -r`), стоит дата съёма.

## Обязательные разделы

### `## Jira`

- URL сайта (`https://<site>.atlassian.net`) — сверяется с сайтом из ссылки
  на тикет и подставляется при голом ключе.
- `cloudId` — параметр `getJiraIssue`.

### `## Ветка`

- Базовая ветка (`master`, `main`, …).
- Шаблон имени ветки тикета с примером из репозитория: `PX-1234-short-slug`,
  `feature/PX-1234`, `px-1234_slug`. Slug — 2–4 слова латиницей через дефис по
  сути тикета; ключ — как в Jira, регистр по шаблону.

## Необязательные разделы

### `## Проверка`

Команды, которыми проверяется имплементация, и откуда их запускать: тесты,
линт, генерация кода, если она обязана быть закоммичена. Одна команда на
строку с комментарием, что она проверяет. Без раздела скилл запускает
очевидное из репозитория и называет это в отчёте.

### `## Верификация`

Кто проверяет, что дифф выполняет критерии тикета (`references/verification.md`).
Одна строка в том же формате, что ревьюер в «Pre-review»:

- `проверяющий: <модель>, усилие: <усилие>`.

Без раздела шага 5б нет: критерии записываются и проверяются шагом 5а, но
никто, кроме автора, не сверяет с ними дифф.

### `## Pre-review`

Кто смотрит дифф до коммита. Каждая строка — ревьюер:

- `ревьюер: <модель>, усилие: <усилие>`.

**Модель** — семейство (`opus`, `sol`) или точный id (`claude-opus-5-5`,
`gpt-6.1-sol`). Семейство значит «самая свежая модель семейства на момент
запуска»: профиль не правится при выходе новой версии, а какая ответила, видно
в отчёте. Точный id закрепляет версию, и расхождение с ним — событие журнала. **Усилие** — уровень рассуждения: `low`, `medium`,
`high`, `xhigh`, `max`; не указано — умолчание механизма.

Как запустить ревьюера, профиль не говорит: механизм выбирает окружение
сессии — встроенные субагенты, оркестратор, CLI провайдера
(`references/pre-review.md`, «Как запустить ревьюера»). Поэтому один профиль
работает и в терминале, и в оболочке с делегированием задач.

Старые строки `субагент: <псевдоним>` и `codex: codex exec review` читаются
как `ревьюер: <псевдоним>` и ревьюер на модели из `~/.codex/config.toml`.

Без раздела pre-review нет: код идёт в коммит после команд «Проверки».

### `## Коммит`

Формат сообщения с примером: `type(scope): PX-1234 subject`, язык subject,
допустимые типы, откуда берётся scope (имя сервиса, каталог). Даёт шаги
«коммит» и «пуш»; без раздела изменения остаются в рабочем дереве.

### `## PR`

Способ создать PR — одно из двух:

- `скилл: <имя>` — установленный у пользователя скилл, создающий PR;
  заголовок и тело пишет он по своим правилам, профиль о теле не знает.
- `gh pr create` — тогда здесь же: формат заголовка, структура тела, базовая
  ветка, draft или нет.

Без раздела PR не создаётся, и призывать некого.

### `## Ревьюеры`

Таблица «имя → команда → ответ»; в команде `<pr>` заменяется номером
созданного PR, `<owner>/<repo>` — репозиторием. Известные способы:

| Ревьюер | Команда | Ответ |
| --- | --- | --- |
| GitHub Copilot | `gh api -X POST repos/<owner>/<repo>/pulls/<pr>/requested_reviewers -f 'reviewers[]=copilot-pull-request-reviewer[bot]'` | ревью PR от `copilot-pull-request-reviewer[bot]` в `pulls/<pr>/reviews`, срок 30 минут |
| Claude (GitHub Action по `@claude`) | `gh pr comment <pr> --body '@claude'` | ревью PR от `claude[bot]` в `pulls/<pr>/reviews`, срок 30 минут |

«Ответ» — где появляется ревью этого ревьюера (ревью или комментарий, логин
бота) и сколько его ждать: по нему шаг «Дождаться и разобрать ревью» понимает,
что ответ пришёл, и когда перестать ждать. Без «Ответа» ревьюер призывается,
но не ждётся. Срок снимается с живого PR: сколько бот отвечал на последних
призывах, с запасом.

Бот, который репозиторий запускает на каждый PR сам, тоже строка таблицы:
команда — «нет», «Ответ» — где появляются его ревью. Срок у него обычно не
нужен: его ждут, пока ждут призванных, и не ждут сверх этого. Если бот
отвечает несколькими ревью (сводка и отдельно inline-комментарии) — так и
запиши: разбор берёт все, пришедшие к концу ожидания.

Текст комментария для Claude — тот, на который настроен workflow репозитория
(`grep -r '@claude' .github/workflows`); у команды может быть принят свой.
Живой человек в эту таблицу не попадает: кого из людей звать — решение автора
по ситуации, а не профиля.

### `## Мерж`

Способ мержа для `/ticket-to-pr:done` — флаг `gh pr merge`: `squash`,
`merge` или `rebase`. Способ должен быть разрешён в настройках репозитория
(`gh api repos/<owner>/<repo> --jq '{squash: .allow_squash_merge, merge:
.allow_merge_commit, rebase: .allow_rebase_merge}'`), с датой съёма. Без
раздела `/ticket-to-pr:done` не мержит.

### `## Деплой`

Всё, что нужно `/ticket-to-pr:deploy` (`references/deploy.md`). Без раздела
команда не деплоит.

- **CI-система:** URL, где лежат креды (имена переменных окружения, не
  значения), джоба сборки ветки (шаблон пути), имя статуса этой сборки в
  `statusCheckRollup`, строки консоли со списком собранных и перетеганных
  приложений, откуда берётся коммит сборки.
- **Джоба деплоя:** путь, параметры запуска с значениями по умолчанию,
  шаблон пути приложения (`<domain>/cmd/<svc>/deploy`).
- **Контуры:** таблица «контур (значение параметра) → kubectl-контекст →
  сообщение бота блокировок → логи (адрес, шаблон индекса) → лейбл метрик».
  Прод-контуры помечены.
- **Блокировки:** канал, имя бота, как в сообщении записан сервис и
  владелец блокировки.
- **Общая ветка**, если в контур катят не ветку тикета, а общую ветку, куда
  подмерживают свои (`references/deploy.md`, «Общая ветка контура»): контур,
  шаблон имени, как найти текущую, параметры запуска, скрипт подмержа.
- **Метрики:** адрес API, запрос lag по consumer group, запрос доли 5xx; как
  из имени сервиса получить группу и `app`.
- **Сроки:** CI, сборка, деплой — в минутах, с медианой и p90, по которым они
  выбраны, и датой съёма.
- **Пороги health check**, если не по умолчанию из `references/deploy.md`.

Факты — с датой съёма: контекст, индекс или лейбл после переезда сервиса
меняются.

### `## Статусы`

Путь тикета по workflow и статусы, до которых конвейер его доводит:

- `Путь:` — цепочка статусов в порядке workflow, каждый следующий достижим из
  предыдущего одним переходом: `To Do → In Progress → Code Review`.
- `Старт:` — статус перед началом работы (`In Progress`); даёт шаг «статус
  перед работой».
- `После PR:` — статус после создания PR (`Code Review`); даёт шаг «статус
  после PR».
- `При деплое:` — статус, в который `/ticket-to-pr:deploy` переводит тикет
  в начале: запуск команды и есть решение, что тикет готов к деплою
  (`Ready to Merge/Deploy`).
- `Финиш:` — статус после мержа в `/ticket-to-pr:done` (`Done`); путь должен
  доходить до него.

Ненужная точка не пишется. Имена — как статусы
называются в Jira: переход ищется по статусу, в который ведёт, а не по своему
имени или id — они различаются между workflow. С какими типами задач
проверен путь — с датой: у другого типа workflow может быть свой.
